## What Was Done

The UI side of the release kill-switch for new cash outs, answering the API action list in
[`../../YOM-1057-…/handoffs/2026-09-16-a.md`](../../YOM-1057-api-payout-domain-and-rewards-integration/handoffs/2026-09-16-a.md).

`payout.enabled` is an **environment** switch — `AppSettings:PayoutEnabledEnvironments`, committed
as `Staging, Production`, so Local and Dev are off. It governs **initiation only**: the API leaves
resume, the hosted session, webhooks and reconciliation alone.

### Hidden, not disabled

Where the switch is off the entry point renders nothing. A disabled button is reserved for the two
reasons the ledger already shows — an unknown balance, a known zero — and this one is invisible
there. A greyed "Cash Out" with an explanation would advertise a feature that may stay off for
weeks. `/opportunities/discover` went the same way under the framework switch (`25c95e1a`).

`CashOutEntry` is the single implementation for both hosts, so the Marketplace hero and the Yo-ID
wallet card are covered by the one change.

### The way out always stays

A youth with Zlto already reserved keeps their button, reading "Continue cash out", and still lands
on the resume panel. That falls out of the check order: `cashOutEligibility` tests `active` before
`enabled`, the reverse of the server, because the server has no opinion about resuming and the
active-payout branch *is* the resume route.

**The subtle one:** `showOutcome` refreshes the profile, so the moment a payout reaches a terminal
status `active` goes false — and with the switch off, `payoutDisabled` becomes the live reason right
then. Hiding on eligibility alone would have unmounted the dialog as the result arrived. The hide is
gated on `!isOpen`, and `CashOutOutcomeStep` takes a `canStartNew` prop so that screen offers "Back
to my wallet" rather than a "Start a new cash out" the server would refuse.

### Backstop

`mapPayoutFailure` maps the server's verbatim `Cash-out is not available` onto a new
`payoutDisabled` gate, for the race where the switch is flipped between the profile load and the
request. Matched **before** `Cash-out is currently unavailable…`, which is the provider's corridor
list and a different fact — the two read almost alike.

Its copy is deliberately not `providerOffline`'s "try again later": that one is minutes, this one is
open-ended, and neither a horizon nor a "coming soon" is ours to give. It says where the Zlto is,
links to the marketplace, and stops.

### The gallery can no longer miss a gate

`GATE_REASONS` was a hand-written `CashOutBlockReason[]`, which accepts a *subset* without
complaint — `payoutDisabled` compiled and simply never appeared. It derives from `GATE_COPY`'s keys
now, which is a total `Record`, so the list is exhaustive by construction. Fourth instance of
gallery drift, first one closed structurally.

### The gate's missing-field list was landing on the buttons

Reported from a phone: "Our secure payout partner needs these details before you can cash out:"
followed by half a screen of white, then the field list down beside Update my profile.

The list was a *sibling* of the message block, and that block carries `grow justify-center` — so it
took all the free space and centred inside it, pushing every later sibling down onto the `mt-auto`
actions. A sentence ending in a colon was separated from the list that finishes it.

`CashOutMessage` takes `children` now, rendered inside its own column under the body (with `-mt-2`,
since it is a continuation rather than a new section), and the gate passes the `<ul>` there. The
distinction is documented on the prop: a continuation goes inside, a genuinely separate block — the
outcome screen's summary figures, an alert — stays outside, which is where `CashOutMessageStep`
already puts its children and is correct there.

### The dev pages guard on the machine, not the build

Both `pages/dev/*` files gated on `NODE_ENV === "production"`, which also 404s them under
`pnpm build && pnpm start` — a *local* production build, and precisely what you reach for when
something only misbehaves in one (as the `/yoid/opportunities` 502 just did). The guard now serves
the page when `NODE_ENV !== "production"` **or** `NEXT_PUBLIC_ENVIRONMENT === "local"`.

Both halves earn their place. The first covers `next dev` whatever `.env` says, since `.env` is not
committed and a teammate's value is not ours to assume. The second is the repo's own test for a
developer's machine (`server/auth.ts`, `api/services/userPreferences.ts`) and is the only one that
can distinguish a local production build from a deployed one: **every deployed image is built with
`NEXT_PUBLIC_ENVIRONMENT=production`, DEV included** — one image, per-environment runtime config.
So the change widens access locally and narrows nothing.

## Gotchas

- **Never `!profile.payout?.enabled`.** Absent means an API older than 2026-09-16, i.e. no gate at
  all — reading that as "off" hides Cash Out everywhere it works. `=== false`, always.
- **The switch must not be able to hide an open dialog.** Anything new that keys off
  `payoutDisabled` needs the same `isOpen` guard, for the same reason: the profile refresh at the
  end of the flow is exactly when the reason goes live.
- **The two server strings are one word apart.** `Cash-out is not available` is the kill-switch;
  `Cash-out is currently unavailable…` is the corridor list. Order in `MATCHERS` is load-bearing.
- **A derived scene list is not the same as a complete one.** The gate list is exhaustive now, but
  `OUTCOMES` and the resume states are still hand-written, so a new member there will still go
  unrendered.
