## What Was Done

IXO's answer on the iframe arrived, and this is the UI side of it — cut small and deliberately, so
testers can start against STAGE today.

### What IXO actually said

> Keep the payment page embedded, with sign-in and KYC verification opening in a popup and returning
> to the iframe afterwards. WorkOS does not permit sign-in inside an iframe. If our iframe uses the
> HTML sandbox attribute, add `allow-popups` and `allow-popups-to-escape-sandbox`. Keep the "Open in
> a new window" fallback for blocked popups.

It mentions popups, so it reads at first like "open the journey in a new window". **It is the
opposite.** The frame stays; *their* page calls `window.open` for the two steps WorkOS will not
allow to be framed, and returns to the frame afterwards. Yoma opens nothing and can see nothing.

This closes the 2026-09-11 blocker. There was never an allowlist to be granted — WorkOS refuses
framed sign-in outright — so IXO routed around it instead. The epic's blocker row is struck through
and replaced with what the change trades it for.

### Three things that did not change, and one that did

**No `sandbox` attribute, and none added.** IXO's third sentence is conditional and the condition is
false. `sandbox` is deny-by-default, so adding it to satisfy that line would strip scripts, forms,
storage and navigation from a journey that needs all four; `allow-popups-to-escape-sandbox` is
meaningless without it. Written into the component header, because the next person to read that mail
will reach for the attribute.

**Nothing else of Yoma's blocks a popup.** Verified rather than assumed: no `headers()` in
`next.config.mjs`, no security headers on the web ingress (host rewrites and proxy buffers only), no
CSP `<meta>` in `_document.tsx`, and `allow` is a Permissions-Policy delegation list with no popup
feature in it.

**`shouldCloseOnOverlayClick={false}` stays, and is now commented as load-bearing** (owner's
request). It was tidiness before; it is now what keeps the frame alive while the youth is away in a
popup that has to return to it. It also governs Escape — `CustomModal` only registers that handler
when the flag is true — so one flag closes both dismissal routes.

**The escape hatch changed.** It was "Taking a while?" plus the link, four seconds after frame load,
written for a frame that would not render. The new failure is the opposite shape: the frame renders
perfectly and the tap on sign-in does nothing, because the popup was blocked — at any point in the
journey, and undetectable for exactly the reason the refused frame was. So the timer, the spinner and
`statusLoading` are gone; the hint is permanent and reads **"Window didn't open?"**, asking about the
window rather than the page. The lead line now says a separate window is coming, so the popup is
expected rather than alarming and the hint has something to refer back to.

## Gotchas

- **Adding `sandbox` to the iframe will break the journey.** The IXO mail appears to ask for it; read
  the condition. See the component header.
- **A blocked popup is invisible to Yoma.** No event, no return value, nothing cross-origin to read.
  Any future "we noticed the popup didn't open" feature is not buildable without an origin-validated
  `postMessage` contract with the provider, which still does not exist.
- **Do not put the escape hatch back on a timer**, and do not add a second copy of it elsewhere. It
  is one control, in the status slot, permanently — the status slot's fixed height exists so the
  footer never reflows.
- **A tab reload during the popup is recoverable and must stay that way**: profile refresh → active
  payout → "Continue cash out" → fresh session from GET `/user/payout/zlto` (Adrian, 2026-09-18).
  This is why the payment URL is never persisted; do not "fix" the reload case by storing it.
