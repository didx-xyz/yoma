## What Was Done

A way back to money already cashed out: once a youth has completed at least one cash out, the Yo-ID
wallet card offers a link to the wallet the provider holds for them. They sign in there, see what is
in it, and retry a delivery if one did not land. Yoma initiates nothing and claims nothing.

### It is a sibling of `CashOutEntry`, not part of it

The structural decision, and it follows from something already true: `CashOutEntry` renders **nothing**
when the environment kill-switch is off. Wallet access is explicitly independent of that switch —
money already sent is not new initiation — so putting the link inside would make it vanish precisely
when a youth might most need to go and look at their funds. Same for a withdrawn corridor.

So `CashOutWalletLink` is its own component in the ledger's `actions` slot, with no opinion about
eligibility, the gate, or an active payout.

### What it will not say

`walletAvailable` means *a wallet exists*. Not that there is a balance in it, not that a bank or
mobile-money delivery succeeded, not that anything is retryable — `Completed` marks Yoma-to-wallet
completion and delivery happens after it. So the copy describes a destination and never a state, and
the component derives nothing from the flag beyond whether to render.

### Two conditions, not one

`walletAvailable === true` **and** a `walletUrl` that passes an HTTPS check. The flag is the API's
answer about this youth; the URL check is about the environment's configuration, which is where the
realistic failure is — the landing URL is per-environment, and Production **must** override the
committed Test value or the button opens Test. A link to nowhere on a money screen is worse than no
link at all.

### The race Adrian flagged, closed

`showOutcome` fires `getLatestPayout()` and `refreshProfile()` concurrently, so the completion
webhook can land *between* them: the outcome comes back `Completed` while the profile was read a
moment earlier and still says `walletAvailable: false`. The youth would be told their cash out is
complete on a screen with no wallet link.

It now re-reads the profile after observing a terminal `Completed` — only that status, because it is
the only one that flips the flag, and `await`ed so the ledger behind the dialog is right by the time
it is looked at. **Not covered:** a webhook arriving after the dialog closes. Nothing pushes into the
page, so that waits for the next refresh or navigation. Adrian says the same.

## Gotchas

- **Do not move this inside `CashOutEntry`.** It would inherit the kill-switch's `null` return and
  disappear for reasons that have nothing to do with it.
- **The flag is not a balance.** Anything that grows out of it — a figure, a "retry" label, a
  "your money is waiting" line — is a claim the contract cannot support.
- **The wallet URL is not the payment URL.** Durable landing page versus 30-minute session token;
  `isSafePaymentUrl` and `isSafeExternalUrl` are the same check kept under two names precisely so
  the two contracts do not get treated alike.
- **`showOutcome`'s second refresh looks redundant and is not.** If someone "optimises" it away, the
  button goes missing on exactly the screen that should show it, intermittently, depending on
  webhook timing — which is the hardest kind of bug to see in testing.

## Open Questions

- **Should the label name the provider?** Built neutral: the epic rule says never name it, and the
  API's own fields follow that (`walletAvailable`, not `ixoWallet`). But the request that prompted
  this work said "View IXO wallet", and there is a fair argument that naming a third-party
  destination is better for someone about to leave the product — you should know where a link takes
  you. `WALLET_ACCESS_COPY.action` is the one string to change.
- **Marketplace hero too, or wallet card only?** Only the card today, per Adrian. The hero's pill row
  is governed by the design board (A1/A4) and already carries two actions; a third would need a
  design call rather than a code one.
