## What Was Done

Both of Adrian's new contracts, wired end to end on the web side.

### Cancellation: the session moved earlier

The structural change. Eligibility only exists on a session or a matched `latest` read, and Cancel
has to be offered **beside** Continue — you cannot offer it after the youth has been handed to the
provider. So the session is now fetched when the active-payout panel *opens*, not when Continue is
tapped:

- `FlowView.resume` carries the `PayoutSession`. It lives in dialog memory, dies with the dialog, and
  is still never persisted.
- Continue **reuses** it rather than asking again — it was issued seconds ago for this payout. An
  expired session is refetched; `POST` is still never a refresh.
- `CashOutResumePanel` gained a `loading` state, `canCancel`, `onCancel` and `onCheckCancel`.

Three new views — `cancelConfirm`, `cancelling`, `cancelled` — plus a refusal that returns to the
panel with a notice rather than becoming a screen of its own, because the payout is untouched and
the panel is what should be read next.

**Three rules that are load-bearing, all of them about acting on the right payout:**

1. **The id on screen is the id POSTed.** `confirmCancel(payoutId)` takes it from the confirmation
   view. Re-resolving "the active payout" at cancel time would, on a stale dialog, release a payout
   the youth never looked at.
2. **A `latest` read whose `id` does not match the session is discarded**, and the session refetched.
   Not reconciled — applying its `canCancel` would arm Cancel for a different payout.
3. **`canCancel === true` is the only value that offers Cancel.** `null` is *unknown*, and a missing
   button asserts "not allowed" on evidence we do not have; it gets a note and a re-check link
   instead. `settingUp` never offers it at all — Yoma has the payout, the provider does not.

Nothing is released optimistically: the API answers only after the provider agreed *and* the
reservation was released, so success is the one thing that licenses the success screen.

### Country minimum

Read from the profile — the same figure the server checks, so no extra request — and shown under the
field from first paint, because discovering a floor only after typing an amount wastes the youth's
time.

**Compared against the conversion preview's USD figure.** Not the typed ZLTO (different unit) and not
a threshold back-calculated from the displayed rate (rounded for display, so wrong precisely at the
boundary). `preview.state === "ready"` already guarantees the estimate belongs to what is in the
field, so a stale preview cannot qualify a smaller new amount. Equal passes, as server-side.

`lib/payout/minimum.ts` holds the rules, with the three ways to get this wrong written at the top.

**An unusable minimum suppresses the claim, not the flow.** A non-USD or negative figure shows
nothing — any figure would be invented — but blocks nothing client-side. The server enforces the real
rule; blocking on contract data we cannot read would lock a youth out of their own money over
someone else's bug.

The server's refusal maps to a new `belowMinimum` failure and a field error that **quotes no
figure**, then refreshes the profile so the hint corrects itself. Parsing the number out of the
server's sentence would be a contract nobody agreed to, and the one we held was just proved stale.

## Gotchas

- **Never re-resolve the payout at cancel time.** The id travels with the view for exactly this
  reason. Same for the eligibility re-check: mismatch means discard, not reconcile.
- **`canCancel` is three-valued and `null` is not `false`.** `=== true` everywhere; truthiness here
  silently turns "we could not tell" into "you cannot".
- **The minimum is USD and the field is ZLTO.** Any future comparison must go through the preview.
  The moment someone compares the typed figure to the minimum, it will look right in testing (the
  rate is ~45, so the numbers are far apart) and be wrong in production for a different rate.
- **Cancel sits between Continue and Close and looks like Close.** Deliberate: cancelling is a
  legitimate choice, not a destructive one, and the confirmation step is what makes a mis-tap cost a
  screen rather than money. If that confirmation is ever removed, this needs revisiting.
- The resume panel now makes a provider request on open. That is the trade Adrian asked for — one
  request earlier, not an extra one — so do not "optimise" it back to Continue-time.
