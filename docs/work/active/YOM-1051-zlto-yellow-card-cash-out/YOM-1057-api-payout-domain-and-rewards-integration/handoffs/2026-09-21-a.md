### USD-only scope — do not build a multi-currency flow

Both currencies are currently USD. The separate profile fields distinguish the current country's
new-payout rule from an already active payout, and retain the original active-payout currency
semantics. This is a small contract clarification, not speculative currency infrastructure.
Do not add a currency selector, country-local FX conversions, or infer a payout currency from
the user's new country. Continue using the existing USD conversion preview and USD formatter.
True multi-currency payouts would require explicit provider, Treasury, validation and UI work;
adding an enum value or exposing these fields would NOT be sufficient.

An unknown/mismatched minimum currency must never be compared numerically against the USD
preview as if equivalent. Treat it as unsupported contract data, not an instruction to convert.
The backend rejects a non-USD currency when a minimum is supplied.

### Wiring and validation

1. Extend the payout-country TypeScript model with nullable `minimumAmount` and currency. Do not
   change the general country lookup contract: these fields belong only to payout countries.
2. Extend `profile.payout.countryAvailability` with `minimumAmount?: number | null` and
   `currency?: Currency | null` (USD is a STRING enum). Optional tolerates rolling
   deployment against an older API. Existing amount/currency remain active-payout-only.
   A supported country supplies countryAvailability.currency=USD even if minimumAmount=null; an
   unspecified/unsupported/offline country supplies neither minimum field. Changing country
   must not relabel an active payout. Use countryAvailability.currency for the minimum message,
   payout.currency for the active payout, and compare only like currencies in the conversion preview.
   CountryAvailability keeps supported/offline and adds these two nullable fields.
3. Use the PROFILE limit for the logged-in user's country in the cash-out initiation popup.
   No extra request on popup/profile just for limits. Show the USD minimum before initiating.
4. Reuse the existing debounced conversion preview; compare its returned USD amount against
   the minimum. Do not compare a ZLTO input directly with USD or reverse-calculate a threshold
   from the rounded display rate. Only use a preview belonging to the CURRENT input; pending,
   stale or failed conversion must not enable continuation on an earlier qualifying amount.
5. When the minimum is non-null, block review/confirmation below it; equal is allowed. Do not
   substitute null/missing with a made-up minimum. Retain positive whole-ZLTO and balance checks.
   Use existing formatters and provider-neutral wording; label the unit clearly as USD.
6. Unsupported/offline country remains blocked by existing flags, even with a null minimum.
   An unspecified user country also returns payout.countryAvailability.minimumAmount=null and remains blocked by
   the existing country requirement. Null must never be interpreted as permission to cash out.
   Refresh/re-evaluate metadata when profile country changes. Profile/cache data is guidance;
   server initiation validates again, so a race with a rate/limit change can still return HTTP 400.
7. Handle the validation message via the existing form/server-error path:
   `The minimum cash-out amount for your country is 7.00 USD` (7.00 is an EXAMPLE ONLY).
   Preserve the entered amount and let the user adjust it. Other server errors remain visible.
8. Do NOT apply this new-entry gate to an existing payout's Continue, outcome or cancellation flow.
   Do not claim the country minimum guarantees acceptance by every hosted payout method.

### UI test matrix

- Missing/null minimum: existing flow unchanged, no minimum message.
- Supplied minimum: below rejected, exact equality accepted, above accepted; unavailable wallet
  or insufficient ZLTO balance still blocks independently.
- Change input quickly around threshold: stale preview never qualifies a lower new input.
- Change country: displayed minimum follows new profile country, not stale previous country.
- Active payout below a newly changed minimum: Continue remains available if canResume=true.
- Server rejects after a rate/limit change: useful error, no second payout/reservation, input kept.
- Existing supported/offline/canResume/enabled behavior stays intact.

## Gotchas

- Minimums will remain null against the current IXO response: this is preparation, not an enabled
  minimum gate. No invented provider JSON field is accepted prematurely.
- Final review supersedes the earlier parent-level proposal: minimumAmount and currency belong
  under payout.countryAvailability. Parent payout.amount/currency remain active-only.
  There are no parent minimumAmount/minimumAmountCurrency fields.
- A country floor is not every corridor's floor. IXO is still the final authority after destination selection.
- Changes in country support/minimum must not strand an already-reserved payout; only creation checks it.
- Shared ZLTO wallets are not environment-isolated. This session made no real payout/provider requests.
