## Jason — UI implementation and test checklist

### Why CanCancel is not on UserProfilePayout

CanResume is local guidance: an active payout has a provider reference and can request a session.
CanCancel depends on IXO's current state. Yoma Processing represents both IXO initiated (cancellable)
and processing (already submitted, not cancellable), so it cannot supply an accurate local flag.
Adding live eligibility to profile would add a provider request to general profile loading, and
the answer could still be stale before the user acts. Fetch eligibility on demand, close to the
interaction instead. Session/latest-info canCancel is only UI guidance; IXO's atomic cancel operation remains
the final authority, including a race with submission in another tab. A profile field would not
remove that execution-time check.

### Agreed dialog flow

- Two on-demand sources now expose eligibility: start/refresh PayoutSession has boolean canCancel
  and payoutId; GET /api/v3/user/payout/latest returns PayoutTransactionInfo with id and nullable
  canCancel. The IDs refer to the same Yoma payout transaction. Profile retains CanResume but has no CanCancel.
- Latest-info uses an IXO status GET only for active reward payouts with a provider reference.
  It does NOT create/refresh a session, reconcile state, settle funds, or fetch reward balances.
  Terminal payouts return false locally. Missing provider reference or failed/invalid provider
  response returns null while retaining local payout information. No payout still returns 404.
- Latest-info status remains the recorded Yoma status; canCancel is live provider guidance.
  They can temporarily differ until webhook/reconciliation updates local state. A false flag
  does not mean local settlement is complete; retain existing outcome handling.

- For an active payout, use the existing CashOutDialog/CashOutResumePanel. Suggested wallet
  button label: "Manage cash-out", making both actions discoverable.
- When the panel opens without a valid in-memory session, fetch GET /api/v3/user/payout/zlto
  for both Continue URL and eligibility. If a valid session already exists and only eligibility
  needs refreshing, use GET /api/v3/user/payout/latest instead; do not refresh a session unnecessarily.
  Show loading/retry while this runs; never infer cancellation eligibility from profile status or CanResume.
- Once loaded, offer Continue and (only when canCancel=true) Cancel cash-out together, BEFORE
  opening the IXO hosted screen. Cancelling must not require IXO sign-in or verification.
- Move the existing session request earlier; do not add another automatic request on profile load
  or immediately on Continue. Keep the fresh session only in dialog memory, reuse it for Continue,
  and refresh if expired. Never persist the payment URL. Discard stale results after dialog closure
  or a change of payout. Apply latest-info eligibility only when its id matches the displayed
  session payoutId; a mismatch invalidates that session rather than silently targeting another payout.
- For setup/recovery with CanResume=false, retain the existing pending/retry state. Do not offer
  Cancel until a provider-confirmed response supplies eligibility.
- A newly initiated payout already returns payoutId/canCancel; no extra eligibility call is needed.

### Execution and verification

1. Add optional payoutId and canCancel to the existing session response model for rolling deployment.
   Add id and canCancel?: boolean | null to latest-info. Null/missing means unknown: do not enable
   Cancel or claim it is permanently unavailable. Offer retry; only explicit true enables cancellation.
   Show cancellation only when canCancel is explicitly true and an exact payoutId is available.
   Use one appropriate on-demand source; do not add profile RPCs or duplicate session/status calls.
2. Ask for confirmation, disable duplicate submissions, then POST the exact displayed payoutId/id to the
   Yoma endpoint above. Never resolve a newer active payout as a substitute after a stale-screen retry.
3. On 200 OK close the hosted flow and refresh profile/wallet/latest payout. Do not optimistically release
   funds or mark cancelled before success. Country changes/disabled new-payout eligibility must not
   hide recovery actions for an existing reserved payout.
4. Eligibility is a snapshot: the user may submit in IXO after session retrieval. IXO atomically decides
   that race. Current Yoma middleware maps IXO 409 to HTTP 400 with its error message/code, and
   unknown references to 404. Do not assume 409 or a structured payoutStatus on Yoma's error response.
   Display errors and refresh the current state; a refusal is not a successful cancellation.
5. On uncertain/server failures retain recovery options; retry only the SAME payout ID. The normal
   cancelled webhook/reconciliation can complete settlement. Do not start a replacement payout early.
6. Test initiated cancellation, double click/retry, hosted cancel then Yoma retry, submitted refusal,
   expired payout, network failure, and a stale modal belonging to a previous payout.
   Verify one release and no duplicate outcome notification after response plus webhook.

## Gotchas / Open Questions

- IXO 200 replay sends no second webhook. We process the confirmed response too, so replay can recover
  a previously failed local release without depending on another webhook.
- No sign-in is required for IXO's hosted cancellation, but Yoma's own endpoint always requires the
  authenticated owner. Unknown/mismatched provider references never authorize a release.
- Reservation release uses existing provider idempotency for failures between remote release and
  local commit. The test suite mocks persistence; Stage integration remains necessary.
- Existing shared Redis locks have a fixed lease without renewal or owner-token-checked release.
  Committed appsettings uses a 300-second payout lease. The mocked race test proves shared-key
  serialization while the lease holds, not correctness after lease expiry or process suspension.
  Verify deployed timeout/lease settings and response/webhook settlement on Stage; shared lock
  hardening is separate infrastructure work, not silently expanded into this payout branch.
