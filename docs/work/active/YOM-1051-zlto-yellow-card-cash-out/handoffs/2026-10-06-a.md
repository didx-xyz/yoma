## What Was Done

The production change is limited to Keycloak identity processing in `WebhookController`:

1. Continue to fetch the current Keycloak user by the authenticated webhook's user ID.
2. Within the existing per-Keycloak-user distributed lock, look up the Yoma user by ExternalId,
   then by username. The second lookup deliberately preserves CSV/B2B provisioned-user linking.
3. When both lookups fail for LOGIN, initialise a `UserRequest` using the same mapping as REGISTER:
   identity/contact fields, country, education, gender and date of birth. Ensure only the default
   `User` role, following registration's existing non-fatal role-assignment error handling.
4. Existing-user LOGIN and recovery then use the **same LOGIN path**, with **one validated upsert**:
   contact and confirmation synchronization, last-login date, email-action cleanup, wallet scheduling
   and login history. That shared `UserService.Upsert` creates the missing entity or updates the
   existing one; recovery does not perform a separate REGISTER save or a second LOGIN pass.
   The upsert emits the existing referral IdentityAction event once, not a second synthetic
   registration event.
5. Remove LOGIN's ten-second missing-user lookup retry inside the lock. A queued REGISTER cannot
   make progress while LOGIN holds that lock. REGISTER still performs one lookup; UPDATE_PROFILE
   retains its existing retry and does not create a missing user.

`PopulateUserRequestFromKeycloak` and `EnsureDefaultUserRole` are private helpers so REGISTER and
recovery do not drift. The mapping helper fills the entity-level `UserRequest` persisted through
`UserService.Upsert`; it does not build the augmented `UserProfile` model or invoke
`UserProfileService.Update`. UPDATE_PROFILE reuses that existing Keycloak-to-request mapping too.
Existing-user LOGIN keeps its narrower contact synchronization and does not acquire a new
role-assignment side effect. The helper rename and comments clarify this boundary without changing
behaviour.

Added `KeycloakWebhookTests`, driving the public endpoint's actual response-completion callbacks
with the real `UserService` and request validator. Unit fixtures simulate serialization and replay
markers; live HTTP tests separately exercised the actual Redis lock and PostgreSQL persistence.

After independently confirming the wider-suite failures on unmodified `origin/master`, Adrian
requested that the existing referral test fixtures be repaired in this same fix. The repairs are
test-only: current execution-strategy callback signatures, complete usage-status mocks, removal of
redundant mock setups and assertions aligned with the existing production validation messages.
No production referral service or eligibility rule was changed.

### Recovery warning — 2026-10-07

At Robbie's suggestion and Adrian's approval, LOGIN now logs a Warning after both Yoma-user
lookups fail, inside the existing per-user lock and before request initialisation or persistence:

```text
Login: Possible lost REGISTER event; no Yoma user found for Keycloak user '{externalId}' (event '{eventId}'); attempting recovery
```

Both IDs are structured log properties; the supplied event ID is sanitized using the existing
log extension. No email address, phone number or token is added to this warning. Search for the
stable phrase `Possible lost REGISTER event` in Datadog at Warning level, then correlate using
the Keycloak user ID and event ID. No Datadog monitor or configuration was changed by this work.
The wording identifies a possible lost registration event, not a proven failure: LOGIN may
arrive before REGISTER during normal event reordering.

The existing successful-recovery Information log remains after the validated upsert. Existing
failure logs remain unchanged. The warning therefore exposes an attempted recovery even if
Information logging is disabled or persistence subsequently fails; it does not claim success.
Existing/provisioned users and suppressed replayed events do not emit this warning. A genuinely
new recovery attempt following a failed save can emit another warning, as intended.

Only logging changed in production. Request mapping, lock/replay policies, persistence, role
assignment, login effects and the accepted first-session token caveat are unchanged.

## Accepted First-Session Caveat and Future UI Follow-Up

This is a conditional recovery edge case, not a change to every user's normal login:

1. REGISTER did not run, so the account has no Yoma user and may also lack Keycloak's default `User` role.
2. Keycloak issues the first token before the asynchronous LOGIN webhook restores that role.
3. Recovery creates the Yoma user and restores the role, but cannot change the already-issued token.
4. A profile request with that stale token can return **403**, even though recovery succeeded.
5. Signing in again obtains a fresh token containing the role; the profile request then succeeds.

The real Keycloak test observed **403 with the first token, then 200 after a fresh sign-in**.
Adrian reviewed and accepted this behaviour for the surgical fix. The current user action is to
sign in again after recovery; this is not an unresolved API implementation requirement or a reason
to bypass authorization.

**Deferred owner: Jason / Web.** If this becomes a recurring UX problem, evaluate obtaining a fresh
token or prompting re-authentication, followed by a bounded profile retry. Do not repeatedly retry
the same stale token or assume that every 403 means registration recovery. The final UI approach
must distinguish this recoverable timing case from genuine authorization failures. No UI refresh,
retry or re-authentication orchestration was added in this branch; that follow-up is not required
to release this fix.

## Gotchas

- **Webhook work remains asynchronous.** ACK 200 does not prove the database save has finished.
  The first profile request can race processing. Tests wait for durable state, not just the ACK.
- **A failed event's replay marker remains, as before.** A new LOGIN event can retry immediately;
  resending the same event ID inside its configured TTL remains suppressed.
- **No universal lock rewrite.** This patch removes the local LOGIN wait/REGISTER contention only.
  It does not introduce lock fencing, lease renewal or a cross-identity account-merging policy.
- **Local isolation:** the cached Docker API image was from CF work and incompatible with master's
  plain PostgreSQL image. It was stopped, the fix branch was rebuilt, and tests used a new local
  `yoma_login_recovery` database. No existing database was deleted or reset, and unrelated running
  containers were untouched. The test-only compose override is outside the repository; normal
  Docker configuration remains unchanged.
- SSI background processing was disabled for Local in that temporary test process. Wallet tests
  verify scheduling, not live provider wallet creation or funding. No Stage/Production data or
  financial transactions were changed for this work.
- The complete automated suite's existing integration fixture also starts the Local API host and
  uses the developer-managed local database. SSI was disabled with a process-only override for
  this run; repository configuration and credentials were not changed. Local notification sending
  remained disabled by the existing environment gates.
- Both test API instances were stopped after verification; the temporary peer container was removed.
  Synthetic test-wallet records remained Pending; do not run provider wallet-creation jobs against
  these disposable test identities. No Stage/Production data or provider wallets were funded.
