The note appeared on **both** `TreasuryOverview` and `OrganizationRewardStats` and would have an admin leave a pool blank believing it safe. Both replaced. `OpportunityRewardContext`'s "No cap — unlimited" was already correct. Recorded as a domain rule and a Decision, because T5 and T6 must not reintroduce it.
2. **`Program.referrerBalance`** — the API has returned it all along; `AdminProgramInfo` was subtracting `referrerLimit − referrerTotal` client-side. Same rule as the reward balances: server-derived, display-only.

Plus two youth-facing `zltoEarned` figures moved off `toLocaleString` onto `formatZlto` (`ReferrerStats`, `ReferralStatsSmallLink`) — reward fields in the referral domain, and T6's grep would have flagged them. `?? 0` preserves the existing "show 0, not a dash" behaviour on those surfaces.

## Gotchas

Carry these forward.

- ⚠️ **A `null` pool means UNLIMITED, at every level.** Not "blocked", not "zero". This is the single most dangerous thing to get wrong in the remaining copy, and it was wrong in two shipped components until this session. Any new empty-pool note must say "not capped".
- ⚠️ **Referral rewards are ZLTO and are capped by the Treasury's ZLTO reward pool — never by the USD payout pool.** The payout figures have no business on any referral surface.
- **Referee before ambassador.** Every partial-payout explanation has to say so, or an admin reading a reduced ambassador figure will think it is a bug.
- **The referral capacity notice is soft by necessity.** `ProgramRequestValidator.cs` never looks at the Treasury. If a future ticket asks for a hard block, it needs an API rule first — do not fake one client-side.
- **The edit wizard's notice drops the programme cap when the typed pool differs from the saved one.** A typed pool has no server-derived balance, and the UI does not compute balances. Understating the cap is safe; inventing one is not. Do not "improve" this by subtracting the cumulative client-side.
- **`RewardStatGroup` defaults to `columns={4}`.** The new groups pass 2, 3 or 4 explicitly — five stats use 3, and the row uses 3 only when a Treasury is supplied.
- **`ProgramInfo` (the public payload) `[JsonIgnore]`s `ZltoRewardPool`, `ZltoRewardBalance`, `MultipleLinksAllowed` and `ReferrerTotal`.** The new components take the admin `Program` shape; do not point them at `ProgramInfo` expecting a pool. The web's `ProgramInfo` interface also still omits `referrerLimit`, `referrerBalance` and `countries`, which the API *does* return — additive, nothing crashes, but a youth-facing surface wanting them needs the interface widened first.
- Everything from the 2026-08-06 and 2026-08-07-a handoffs still applies: the three Treasury payout figures, pending surviving rollover, the client-derived pending total, full-replacement PATCHes, message-text server-error matching, 401-not-403, wallet nullability, rewards having no available-balance equivalent, ZLTO as the only reward asset, and the `?mock=` dev aid needing removal before merge.
