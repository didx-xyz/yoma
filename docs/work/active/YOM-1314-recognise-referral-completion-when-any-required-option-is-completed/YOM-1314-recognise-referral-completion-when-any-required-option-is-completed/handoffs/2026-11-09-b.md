## What changed

Adrian approved adding a reusable manual job, instead of an ID-specific recovery endpoint. This supersedes the earlier recovery-trigger deferral; no database repair is included.

- Added `ILinkUsageBackgroundService.ProcessPendingProgress(CancellationToken)` and implementation.
- Registered **Referral Pending Claim Progress (manual only)** with Hangfire `Cron.Never()`.
- Snapshot only distinct user IDs with Pending claims, then process sequentially, once per user, with a fresh DI scope. This is intentionally not offset paging over a shrinking queue or repeated selection of the first Pending batch.
- Call normal `ILinkUsageService.ProcessProgressByUserId`: per-user locks, transactional status rechecks, existing rewards/counters and notifications remain authoritative.
- Global sweep lock uses the existing ownership-checked `TryRunWithLockAsync` wrapper with zero acquisition wait. An expired owner cannot release a successor's lock. Existing schedule maximum interval and lock buffer bound dispatch; no new configuration. In-flight user processing is awaited, not forcibly interrupted inside its transaction. Leases are not renewed: an exceptionally long in-flight call can exceed the lease; existing per-user/transactional state checks remain necessary.
- Check Hangfire cancellation between users; the shared wrapper releases ownership in finally. User failures are logged and other users continue; the job fails visibly at the end if any failed. Automatic exception retries are disabled on the interface method used by registration; an actual Hangfire filter-provider test verifies this. Interrupted executions may still be requeued by Hangfire's shutdown recovery.

## Run instructions after deployment

1. Verify the new API deployment and refresh the Pending/overdue audit.
2. Open the existing authorised Hangfire dashboard, **Recurring Jobs**.
3. Select **Referral Pending Claim Progress (manual only)** and choose **Trigger now** once. The registration has no automatic schedule.
4. Monitor the enqueued job and logs. Counts report users successfully evaluated, not claims completed. A user can remain Pending, complete, or expire under existing rules. Failures and a processing-time cap require review before manually triggering again.
5. Reconcile claim status, reward schedules and counters. A subsequent invocation resnapshots remaining Pending users; claims already Completed are not rewarded again.

The ID snapshot excludes users whose first Pending claim is created after the snapshot; normal events or a later sweep handle them. For a selected user, the existing processor checks all their then-Pending claims. Memory grows with distinct user IDs only, not hydrated claim records. No per-claim list or private participant data is committed.

## Historical recovery remains separate

Overdue Pending claims are expired by the normal processor before completion evaluation. Already Expired, Abandoned and Initiated claims are not selected. This job does not bypass deadlines, reset states or change dates. Any manual reopening requires separate evidence review and preservation of original status/dates; no blanket resets or extended deadlines are part of this change.
