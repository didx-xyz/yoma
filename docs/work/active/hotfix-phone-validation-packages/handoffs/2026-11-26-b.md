## What Was Done

Root cause found before changing anything. Keycloak's `libphonenumber 8.13.7` (Feb 2023) carries a UG mobile pattern that rejects `0745`–`0749` and `0790`–`0797`; the Keycloak UI and web both accepted those, so users only failed at the server-side `Utils.canonicalizePhoneNumber` → `isValidNumber` step. Verified by running both jars against the same inputs:

| Prefix | Java 8.13.7 | Java 9.0.44 |
| --- | --- | --- |
| 0740–0744 | ✓ | ✓ |
| 0745–0749 | ✗ | ✓ |
| 0790–0795 | ✗ | ✓ |
| 0796–0797 | ✗ | ✗ (unassigned per ITU) |
| 0798–0799 | ✓ | ✓ |

Changes:

| Component | Package | Previous | Updated |
| --- | --- | --- | --- |
| web | libphonenumber-js | 1.13.2 (lock) | 1.13.17 |
| Keycloak provider | com.googlecode.libphonenumber | 8.13.7 | 9.0.44 |
| Keycloak theme | intl-tel-input (vendored) | 25.10.6 + utils from jsDelivr CDN | 29.5.12, `intlTelInputWithUtils.min.js` (utils bundled, no CDN) |

## Gotchas

- intl-tel-input ≥ 27.0.1 uses `Object.hasOwn` (ES2022) at init. Adrian's review reproduced the failure on browsers without it; `intlTelInputDirective.js` now defines a fallback before `Vue.directive(...)`, verified by deleting `Object.hasOwn` in a page init script and watching the input initialise and validate. The review also found the directive was still loaded at its unversioned URL (cached v25 init code + v29 library); all four templates now load `intlTelInputDirective.js?v=29.5.12`. Both are in the rebuilt `keycloak-phone-provider.resources.jar`.
- v27 made `getNumber()`/`isValidNumber()` throw when utils are not loaded. The bundled build makes that impossible here; do not switch back to the split `intlTelInput.min.js` + `loadUtils` without also awaiting `iti.promise` in the four templates.
- The dummy SMS sender (`DummySmsSenderService`) randomly fails 20% of sends with "Insufficient credits to send message" (503). That is simulated, not a regression.
- `kc_action=UPDATE_PHONE_NUMBER` on the auth URL returns `kc_action_status=error`: the required action does not implement `initiatedActionSupport()`. Pre-existing; the API sets the required action on the user instead.
- Local Keycloak posts forms to `http://keycloak:8080` (`KC_HOSTNAME`), so the browser must resolve `keycloak` → 127.0.0.1 or every form submit ends in "Cookie not found".
- Keycloak caches theme resources for 30 days under a path keyed to the Keycloak build, not the theme; any further change to `intlTelInput.css`/`flags*.webp`/`styles.css` needs a new `?v=`.
