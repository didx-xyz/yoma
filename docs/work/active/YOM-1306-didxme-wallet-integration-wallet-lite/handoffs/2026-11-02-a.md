## Request Failure Classification

Production v3.13.7 reported `Unexpected end of request content` while reading the incoming
request body, before the opportunity search action. The API middleware treated this request
failure as an unexpected Error/500.

- Both exception middleware components now recognize `Microsoft.AspNetCore.Http.BadHttpRequestException`,
  including server-specific subclasses, and retain its actual HTTP status (for example 400 or 413).
- Expected 4xx failures use Information logging with the existing exception, method/path, type,
  status and message diagnostics. Other statuses remain Error; genuine unexpected exceptions remain 500.
- The response retains the existing error-item array. A disconnected request gets no new body;
  a started response rethrows the original exception without changing its status, headers or body.
- Cancellation or I/O failure during error writing is suppressed only when the request-aborted
  token confirms disconnection. Other write failures still propagate.
- No search, database, frontend, provider infrastructure, timeout or deployment changes.

The base/subclass relationship and status property are documented by
[Microsoft](https://learn.microsoft.com/en-us/dotnet/api/microsoft.aspnetcore.http.badhttprequestexception?view=aspnetcore-10.0).
Tests exercise the actual Kestrel subclass using its non-public constructor, without a running server.
