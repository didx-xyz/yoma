## What Was Done

- Profile changes queue a `DateRefreshRequested` marker in the existing issuance table, in the same transaction as the user save. No provider request runs in the profile flow. Both `UserProfileService.Update` and `UserService.Upsert` share `UserExtensions.ComputeProfileHash`, built on Core hashing. It compares stored profile values before/after existing normalization and ownership rules; login/audit timestamps, resolved labels and settings do not count as profile edits. Internal upsert still preserves profile fields once the user is linked. Photo replacement/removal also queues the check; deleting an absent photo remains a no-op.
- Issued credentials move to explicit `Reissue` status when a profile change is queued. `SSIBackgroundService` compares the actual signed YoID claims against current values using its issued schema version. It reuses the issuance attribute mapper extracted into `SSICredentialAttributeHelper`. Unchanged signed values clear the request and restore `Issued` without replacement. New fields only present in the latest schema do not trigger replacement. Pending/Replay rows keep their state and marker until successful issuance moves them to `Reissue`; comparison failures retry as `Reissue` through the common error policy.
- A changed YoID moves to `Revoke`; one fresh `Pending` child is created with `ParentId` pointing to the previous issuance. The child cannot issue until the parent's revocation is confirmed. It uses the configured YoID schema name, latest version at issuance, its own schedule/referent and a new issue date. The old wallet copy is deleted only after the child has issued; the old row, IDs, version and issuance date remain as history.
- `Revoked`, `Deleted`, `DateRevoked` and `DateDeleted` record confirmed progress. Wallet list/detail retain confirmed revoked copies with `status: Revoked` until deletion succeeds, even if cleanup exhausts retries. A replacement appears separately as `Issued`; during replacement there can be a period with only the revoked copy available. Ordinary Replay keeps its existing same-row/original-date behavior, and opportunity credentials are unchanged.
- Existing background job limits, distributed locking, scoped dependencies and common retry/error handling remain in use. Root-row locking serializes refresh/child creation. A newer refresh marker cannot be cleared by an older comparison, and changes arriving during delivery are checked afterwards. Lifecycle transaction retries clear EF tracked state between attempts.
- The didx:me adapter uses retained issuer references to request revocation and checks the resulting status before confirming success. An already revoked result is idempotent recovery. Aries reports unsupported capability, so it keeps the current credential and clears the refresh request without retrying unsupported work.
- Added migration `ApplicationDb_SSI_YoID_Replacement`: nullable lifecycle fields/self-reference, four status lookup rows (`Reissue`, `Revoke`, `Revoked`, `Deleted`), one root schedule per existing identity, and at most one child per parent. Existing rows remain unchanged; deployment does not mass-replace credentials. Rollback deliberately refuses to collapse replacement history.

- Review follow-up: use generic reissuance terminology for the workflow and logs (`ScheduleReissuance`, `ProcessReissuance`, `ListPendingReissuanceSchedule`, `ReissueCredential`). YoID remains the current eligibility rule; no additional credential family is enabled. Expanded XML summaries and logical spacing, and moved the three lifecycle dates immediately before audit dates in the model, entity and repository mappings. These are naming/layout changes only.

## Gotchas

- Revocation requires the original issuer/session references. A credential previously recovered without its issuance journal remains readable, but this revocation path stops safely if those references are absent. It must not guess an issuer ID or substitute wallet deletion for revocation. Reconcile such records before retrying replacement.
- If revocation fails permanently, the original remains visible and the pending child stays blocked. If replacement fails after confirmed revocation, the old credential remains visible as `Revoked`; retry the child. If wallet cleanup fails, the replacement remains usable and the old row retains its revocation timestamp.
- Error rows need an operator to restore the appropriate lifecycle phase after fixing the cause. Do not turn a revocation or cleanup failure into ordinary Pending work, or manually Replay historical parents.
- A photo upload creates a new stored photo even when its bytes match an earlier upload; it remains a real profile-reference change. The signed-value comparison is still the final replacement decision.
- Wallet list/detail add a lifecycle `status`; Jason must implement the tags described below. Request payloads and deployment configuration are unchanged.

## Jason — wallet status tags

- `Issued`: the provider reports issued/not revoked, or the credential has no revocation mechanism. `Revoked`: the provider reports revocation. `Unknown`: its current lifecycle could not be established; do not label it active or revoked. These statuses are not signature, expiry or proof verification. External revocations are reflected when the provider reports them.
- **Credential detail popup:** `SSICredential` retains lifecycle `status` and adds `verificationStatus: "Unknown" | "Verified" | "Invalid"`. Bind the verification badge to this separate field. Lifecycle and verification are distinct; show Revoked clearly when present. Treat missing fields from an older API as unspecified, not Verified.
- `Invalid` includes confirmed revocation; render "Invalid — revoked" when status is Revoked. Do not rename revocation to Withdrawn. These verification labels are Yoma's API contract, not a universal SSI enum. Unknown means not established/unavailable, not Invalid.
- **Temporary behavior explicitly requested for this release:** Issued maps to verificationStatus Verified, Revoked to Invalid, and Unknown to Unknown. Verified is currently an assumed presentation default, not a completed verification. No signature, disclosure, expiry or proof check is added, and there is no verification timestamp. Do not use this placeholder to authorize access, rewards or proof acceptance, or describe it as a fresh cryptographic check.
