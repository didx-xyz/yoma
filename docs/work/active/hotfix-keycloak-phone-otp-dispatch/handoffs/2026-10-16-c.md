## What Was Done

- SRE reviewed #1979 and asked for three things: tell users when a message was sent but delivery is unconfirmed; return 400 rather than 5xx when the number can't be reached, with SMS fallback for ZA only; and rate limiting where needed. Jason chose to rework the PR rather than ship it as a stop-gap. The behaviour now follows the outcome table in [feature.md](../feature.md#plan).
- Sender: polling continues past `sent` to `delivered`. If the window ends at `sent`, non-ZA numbers get `DELIVERY_UNCONFIRMED` (code saved, warning shown) and ZA numbers get the SMS backup again. Twilio recipient error codes (21211, 21614, 63003, 63024) → `MessageRecipientException` → 400; everything else → 503. User-facing error text now says what happened.
- Rate limiting: failed sends are recorded as pre-expired `FAILED` rows in their own transaction and count toward the existing limits. The limits now use `>=`. Duplicate live codes no longer cause a 500.
- Theme: an unconfirmed-delivery warning on the four main phone pages, plus `codeSentUnconfirmed` in all five locales.
- Validation:
  - **Harness**: 17 sender scenarios pass against the rebuilt JARs (scripted fake Twilio, nothing sent).
  - **Local Keycloak 26.4.0 with the dummy sender**, rebuilt JARs loaded, unauthenticated endpoint calls only:
    - Response includes `delivery_confirmed`.
    - A dummy 503 left a `FAILED` row that survived the rollback.
    - The per-IP limit blocked at exactly 10, counting that failure.
    - 3 seeded failures blocked the number at exactly 3.
    - `FAILED` rows don't trigger `ALREADY_SENT`.
    - Two live codes give `ALREADY_SENT` with the newer expiry, instead of a 500.
    - The registration page renders the new alert in English and French.

  All test rows were deleted afterwards.

## Gotchas

- Keycloak's `KeycloakErrorHandler` marks the request transaction rollback-only. Anything written before an error response is lost unless it goes through `KeycloakModelUtils.runJobInTransaction`.
- The server round-trips `codeSendStatus` and only carries `expiresIn` through for `SENT`/`ALREADY_SENT`. New alert variants need a separate flag, not a new status.
- Local test numbers must pass libphonenumber validation; the fictional UK `07700 900xxx` range is rejected. Repeated local sends hit the 10-per-IP limit within the hour; delete the rows from `phone_message_token_code` to reset it.
- A non-ZA user whose message stays at `sent` waits the full ~14 s again (vs ~2 s in the first version) before seeing the warning.
