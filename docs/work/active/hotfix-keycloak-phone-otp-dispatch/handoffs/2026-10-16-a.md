## Impact and conclusion

**This failure blocks phone registration and phone-number verification for affected users.** The same sender is shared by phone OTP login and reset-code routes, so those routes can also be affected. It is not evidence that all authentication, email registration or social login is unavailable.

The supplied Production investigation reports WhatsApp messages reaching `sent`, but not `delivered` during the synchronous check window. The custom provider treats that as failure, attempts SMS, then rejects the non-South-African number. Keycloak returns HTTP 503 and Traefik passes it through.

The repository confirms that exact control flow. The reported counts, handset receipt and live Twilio message histories were not independently queried in this session.

3. `src/keycloak/providers/keycloak-sms-provider-twilio/src/main/java/cc/coopersoft/keycloak/phone/providers/sender/TwilioSmsSenderServiceProvider.java`, lines 75-83: tries WhatsApp and falls back to SMS if it throws.
4. The same file, lines 155 and 183-235: polls the created message; only `delivered` and `read` return success. `sent`, `queued` and `sending` keep polling. Exhausting eight checks throws an uncertain-delivery exception.

Receipt on the handset is not proven by a `sent` status, but if it does arrive this explains why it may still not work.

## Recommended immediate fix: small and explicit

Jason should branch from current master and modify the Twilio sender only, plus focused tests and its rebuilt JAR. No API or web contract change is needed for this dispatch fix.

### 1. Accept `sent` as successful dispatch

In `TwilioSmsSenderServiceProvider.checkMessageDeliveryStatus`, move `sent` out of the continue group and give it an explicit return:

```java
case "sent":
    logger.info("WhatsApp message " + messageSid
            + " dispatched; delivery is not yet confirmed");
    return;
case "queued":
case "sending":
    // Still processing; retain the existing bounded checks.
    continue;
```

Keep `delivered`/`read` success and `failed`/`undelivered` failure unchanged. Keep the retry count/delay unchanged for this hotfix. Update the method summary/comment to distinguish dispatch acceptance from confirmed delivery.

In `sendMessage`, replace the misleading outer `WhatsApp delivery successful` log with wording such as `WhatsApp dispatch accepted`. Do not claim handset delivery just because `sent` returned.

This fixes the reported `sending -> sent` sequence without redesigning the sender. It stops polling once `sent` is seen, but does not guarantee instant responses: earlier queued/sending states can still consume part of the existing wait window.

### 2. Preserve the established boundaries

- Leave `DefaultPhoneProvider.sendTokenCode` and its persistence order intact. Successful dispatch now lets the existing code persist the original OTP normally. Do not persist an OTP before a genuinely unsuccessful send just to hide the error.
- Leave code matching, expiration, consumption and phone-verification rules unchanged. Successful dispatch must never mark a phone verified; the user still has to submit the valid OTP.
- Preserve the same OTP for supported SMS fallback. Preserve South-Africa-only SMS; do not enable international SMS or change billing/configuration.
- Preserve real send exceptions and terminal WhatsApp failure handling. Do not replace the whole sender with unconditional success or swallow all exceptions.
- Keep email/social login, registration linking, webhook recovery and SSO configuration untouched.
- A message can fail later after `sent`; this fix accepts dispatch, not guaranteed eventual delivery. User retry remains necessary if no code arrives. Asynchronous delivery tracking is a separate enhancement, not required in this patch.

### 3. Do not silently expand this emergency patch

The supplied analysis says no limits exist. That is not correct: `DefaultPhoneProvider` calls `isAbusing` and `ongoingProcess`. `DefaultPhoneVerificationCodeProvider.isAbusing` counts persisted token records by target and source. Since this failed-send path persists none, these attempts escape those counters. Concurrent requests can also pass the initial check together.

Accepting `sent` restores normal OTP persistence and the existing ongoing-code guard for sequential retries in the reported path. It does **not** solve all failed-send/concurrent-request throttling. Counting failed attempts, distributed cooldowns, the existing `>` versus `>=` limit boundary, and classifying unsupported fallback as a clear client error should be a separately reviewed follow-up. Do not add a table, new limiter, broad exception remapping or callback service to this surgical fix.

The immediate patch also deliberately leaves the old timeout/fallback behavior in place when a message never reaches `sent`, `delivered` or `read`. Do not claim that it fixes every 503. If live SID records show the affected messages never reach `sent`, revisit the diagnosis before shipping a broader change.
