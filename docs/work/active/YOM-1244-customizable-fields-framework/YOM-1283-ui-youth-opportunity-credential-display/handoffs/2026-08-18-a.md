## What Was Done

The credential detail modal on the youth passport page now renders the full YOM-1280 wallet
contract: grouped sections, interleaved core and custom-field attributes, and structured Skills.

- **Grouped sections.** Attributes render under the API's `group` / optional `subGroup` as headings,
  built as **consecutive runs** of the same label. Ungrouped attributes render with no heading, after
  the configured groups — which is where the API already puts them. Nothing is re-sorted; see the
  first gotcha for why that is the point rather than an omission.
- **Structured Skills.** `itemsDisplay` renders as individual badges instead of one delimited string,
  matching the skills treatment on the opportunity pages. `valueDisplay` is the fallback only.
- **Extracted `CredentialAttributes`.** The attribute list came out of the page and into a component,
  so the page keeps the fixed header (issuer / artifact type / date issued / schema type) and nothing
  about grouping. `toAttributeSections` is exported separately from the rendering, so the run-building
  rule is testable without a DOM.
- **Model corrected against the running API.** Added `itemsDisplay` and
  `SSICredentialAttributeItem`. Moved `attributes` off `SSICredentialBase` onto `SSICredential`:
  the API omits the property from wallet _list_ items entirely, and `SSICredentialInfo` claiming it
  was simply wrong.
- **Fixed: `activeCredential` was typed as the list item, not the detail response.** It holds
  `getCredentialById`'s result. It type-checked only because the base declared the attributes both
  shared; separating the two surfaced it. Pre-existing.
- **Fixed: the header showed `ACR` to youth.** `artifactType` comes back as the enum _name_, so an
  AnonCreds credential rendered the raw member. It now goes through `ARTIFACT_TYPE_LABELS`
  (added by YOM-1281 for this). Adjacent to scope — revert freely if you want it on its own commit.
- **No mock.** Unlike YOM-1281 / YOM-1282, nothing here was routed through
  `credentialSchemaAdmin.ts`. The provider serves reads, so this whole surface is live-testable, and
  the façade stays a schema-only concern.
- **Modal and card sizing freed up** (Jason). The detail body's fixed
  `overflow-y-scroll md:max-h-[480px] md:min-h-[350px]` came off, and so did the list card's
  `max-h`/`max-w` clamps on issuer and title. Grouped sections make the detail taller than the flat
  list ever was, and a hard-capped scroll box inside the modal was the wrong container for it —
  `CustomModal`'s own `md:max-h-[650px]` still bounds the dialog. Layout only; no logic.

## Manual Test Steps

The API must be running on `feature/custom-fields-framework`, and the passport page needs
`NEXT_PUBLIC_PASSPORT_ENABLED=true` — it renders an "Update in Progress" placeholder otherwise, which
is easy to misread as a failure. No mock is involved: every credential shown is a real one from the
provider, so what is testable depends on what has actually been issued to the signed-in youth.

1. **List.** `/yoid/passport` shows the credential cards, unchanged by this work. Attributes were
   never on the list and still are not.
2. **Generic credential detail.** Open an `Opportunity|Default` credential. The fixed header rows
   render as before, then the attributes appear beneath in the API's order. This is the regression
   case that matters most — the old view rendered these as one flat list.
3. **Group headings.** Confirm each heading matches the API's `group`, with `Group › SubGroup` where a
   subgroup is set, and that no heading repeats.
4. **Ungrouped tail.** Attributes with a null `group` render last, with no heading and no blank
   heading row.
5. **Skills.** A credential carrying Skills renders one badge per skill, not a comma-joined string.
   Compare against the raw response: badge count must equal `itemsDisplay.length`.
6. **Historical Skills.** Open a credential issued before structured Skills existed
   (comma-delimited in the provider). It must render identically to step 5 — the API normalizes both
   into `itemsDisplay`, so a difference here is an API finding, not a web one.
7. **AnonCreds label.** A YoID credential shows "AnonCreds", not "ACR".
8. **Type-specific credential.** Needs a credential issued against a type-specific schema, which
   needs schema creation — see the blocker below. Core and custom-field attributes must interleave
   inside shared groups rather than forming two blocks.
9. **Empty complex value.** A complex attribute issued with no value renders the API's `"n/a"`, not
   an empty row. Only reachable once custom-field credentials are issued.
10. **Long values / narrow viewport.** Badges wrap and the row keeps its label column; check on
    mobile width, where the label's `md:w-64` does not apply.

## Gotchas

- **Do not "fix" the missing sort.** `toAttributeSections` deliberately does not order anything, and
  the epic README's earlier instruction to order wallet attributes through `byPresentationOrder` was
  wrong — it has been corrected. The API returns the collection already ordered and group-contiguous,
  and its rule depends on configured-group precedence the client cannot see. Re-sorting client-side
  would also introduce a comparator that can disagree with .NET's: JS `localeCompare` is
  locale-sensitive where `OrderBy` is not. `groupLabelOf` _is_ shared, so the heading rule is still
  single-sourced.
- **An empty `itemsDisplay` is not the same as a null one.** Null means scalar; `[]` means a complex
  attribute with no value, and the API pairs it with `valueDisplay: "n/a"`. The row checks
  `items.length`, not the property's presence. Checking presence renders a valueless row.
- **Never split `valueDisplay`.** It is a flattened convenience and an individual value may contain
  the delimiter, which is precisely why `itemsDisplay` exists. This is an explicit YOM-1280 decision.
- **Wallet detail resolves the credential's own immutable schema version**, not the latest. A
  credential keeps the labels and mappings it was issued with, so an attribute renaming in schema
  management will not appear on already-issued credentials. Correct, and it will look like a bug.
- **Sections are keyed by position, not by heading label.** If the API ever returned a heading
  non-contiguously, two runs would share a label; a label-keyed map would have merged them and
  silently reordered the response.
- `searchCredentials` and `getCredentialById` still carry large commented-out
  `NEXT_PUBLIC_ENVIRONMENT === "local"` fixture blocks predating this epic. They are stale — no
  `group`, no `itemsDisplay`, and `artifactType: "Indy"` which no longer exists. Delete them rather
  than reviving them if a wallet mock is ever wanted.
- The passport page is gated behind `NEXT_PUBLIC_PASSPORT_ENABLED`, checked server-side in
  `getServerSideProps`. With it off the page renders a friendly placeholder and never calls the API.

## Open Questions

- For Adrian, when convenient: does anything guarantee that an attribute's `group` is stable across
  schema versions? Wallet detail reads presentation metadata from _current_ configuration, not from
  the credential, so re-grouping a core property changes how already-issued credentials render. That
  is presumably the intent of keeping the metadata unsigned, but it means group edits are
  retroactive across the whole wallet and worth stating explicitly somewhere.
- Whether the ungrouped tail should carry a heading of its own ("Other"). Rendering it bare follows
  the contract, but on a credential where _nothing_ is configured the whole list appears headingless.
