### Changes

**B1: merge the untyped credentials into Other, labelled "Other opportunities". Confirmed.**

Why I agree with Jason:

- A youth cannot tell the two groups apart. They have the same colour and the same kind of
  content. "Opportunity" names the *schema family* every non-YoID credential belongs to, not a
  type, so next to "Job" or "Event" it reads as a type that is missing.
- "Other" already means "an opportunity that is not one of the named types". An untyped
  credential is exactly that, from the youth's side.
- The label "Other opportunities" works for both: the Other type and the legacy credentials
  that predate types.

How:

- `lib/typeColours.ts:88-95` `credentialTypeKey`: a non-YoID credential with a null
  `typeContext` returns the Other type's key (`"Other"`), not `null`.
  - So the card chip, the section, the chip and the detail modal all read Other, from one rule.
  - Update its doc comment (`:83-87`). The return type becomes `string`.
- **Assumption (investigator):** `"Other"` is the Opportunity Type enum name in the types lookup.
  It is the key `TYPE_CONFIG` and `cardFacts.ts:98` already use.
- `lib/typeColours.ts:101-108` `credentialTypeLabel`: the `!key → "Opportunity"` branch goes; an
  untyped credential now arrives as `"Other"`.
- `lib/credentials/credentialGroups.ts:32-37`:
  - drop the `key === null` rank, so Other ranks by its lookup position, like every type;
  - drop the `key: string | null` in `CredentialGroup` (`:10`), since no group is keyless any more;
  - unknown keys (a type the lookup does not know) still form their own groups, ranked after the
    lookup's types, as today.
- **Group label:** the Other group's chip and section heading read **"Other opportunities"**.
  - The card chip and the modal keep the *type* label, **"Other"**, the same word the discovery
    card's chip uses.
  - So `CredentialGroup` carries `label` ("Other opportunities", for the chip and heading) and
    `typeLabel` ("Other", for the card). `PassportCredentials.tsx:155` passes `group.typeLabel`
    to `CredentialCard`.
  - Every other group has `label === typeLabel`.
- Within the merged group the credentials keep the API's order: typed and untyped interleave as
  they were issued.
- **Supersedes** the 2026-10-20 Decision clause "then credentials with no supported type
  ('Opportunity')", and the doc comments in `credentialGroups.ts:15-19` and
  `typeColours.ts:97-100`.

**B2: counts on every chip, honest before everything is loaded.**

Decision: **a type count that is not yet final reads "14+"**. Once every page is loaded it reads
the exact "18".

Why "14+", not "14 of loaded" with a hint:

- "14+" is true at every moment. The youth has *at least* 14 Job credentials, and the "+"
  says there may be more. It still says so for a type whose credentials are, by luck, all on
  page 1. That is still true, just not tight.
- It fits the pill (4 characters), and the reason already sits under the content: "Showing 100
  of 130 credentials" above Load more (`pages/yoid/passport/[[...query]].tsx:364-367`). A second
  hint on every chip would repeat that.
- "14 loaded" or "14 of ?" would make the youth do sums. A bare "14" is what is wrong today.

Rules (`components/Credentials/PassportCredentials.tsx`):

- **All** keeps the exact `total` (the API's `totalCount`), always.
- **Type chips** (`:190-191`): always show the count. While `!complete`, append the plus sign:
  `<span className={PILL_COUNT_CLASS}><span className="sr-only">at least </span>{formatNumber(n)}<span aria-hidden>+</span></span>`.
  A screen reader then says "Job, at least 14", not "14 plus".
- **Section heading count** (`:132-134`): the same rule, the same markup.
- **"See all"** (`:136-143`): while `!complete`, read **"See all →"** with no number, which is
  DiscoveryRail's wording when its count is inexact (`DiscoveryRail.tsx:151-153`). When
  complete, read "See all 18 →" as today.
- `complete` is the page's `!hasNextPage` (`:325`), which already exists.
- A type whose first credential is on a later page gets its chip when that page loads, as today.
  Exact per-type counts at every wallet size are **API-gated**: the wallet-search `typeContext`
  filter or a facet count, already asked of Adrian.
- **Supersedes** the 2026-10-20 Decision clause "Type chips show counts only once every
  credential is loaded".

## 4. Colours: revised palette proposal for the BA (D1, D2, D3) and the audit (H2)

### Problem

1. **Learning and Other are the same slate** (`--color-type-default`, `#5a6675`). The untyped
   "Opportunity" group shared it too; it is merged away by §1.
2. **YoID (`#3b1251`) and Event (`#391350`) are indistinguishable:** ΔE2000 = 0.55, which is
   below what anyone can see.
3. **The BA palette fails WCAG AA for its own white text.** The chip (10 px bold) and the action
   button (14 px semibold) are normal-size text, so they need ≥ 4.5 : 1. Job is 3.77, Impact Action
   2.91 and Entrepreneurship 3.18. This was not raised in round 2.
4. **Event is blue on the detail page** (`bg-blue`, 2.48 : 1, `detail-event-1440.png`), purple
   everywhere else. The detail page still colours by `TYPE_CONFIG` (H2).

On D3 ("Event is purple; it should match the BA palette"): the BA's Event *is* purple
(`#391350`, feature.md palette table). I read Jason's point as "the chip colours must match
everywhere". The off-palette Event is the detail page's blue badge, which the audit below fixes.
**Assumption (investigator):** the BA workbook's Event fill is `#391350`.

### Proposal (send to the BA)

- Keep each BA hue.
- Where white text fails, darken in CIELAB (lightness only, so hue and chroma stay) until
  white text reaches ≥ 4.6 : 1, a little over 4.5 for rounding.
- Give Learning and YoID hues no type uses.
