### Shared lifecycle policy

- Inject the host's existing `IHostApplicationLifetime`; do not add public job parameters or
  change interfaces, Hangfire registrations, recurring IDs, schedules or concurrency settings.
- Check `ApplicationStopping` before lock acquisition and immediately after successful
  acquisition. Check again at each job's safe dispatch/batch/page boundary. Do not clear another
  worker's lock when acquisition returns false.
- Let an active durable unit finish, including the existing local persistence after a provider
  success. No cancellation token is introduced into remote calls, execution-strategy bodies or
  transactions. Shutdown does not become a per-record retry/error transition.
- At the job boundary, log shutdown distinctly and propagate cancellation rather than swallowing
  it as successful completion. Existing ordinary error/retry behavior stays unchanged, except
  fatal tenant-worker setup/disposal/persistence failures now surface just as issuance does.
- Release acquired locks through async-scope disposal; do not insert stop checks into cleanup.
  Disposal is outside the job's try/catch/finally, so skill-cache or push-tracking finalizer errors
  cannot skip lock release. The initial extra nested guards are no longer needed.

### Reusable async scope (Adrian's review refinement)

Adrian selected BackgroundJobExecutionScope as the final name to describe one invocation's
coordination/cleanup, not ownership of the host lifetime. The rename covers the type, source/test
files, all 39 callers and this documentation, without changing behavior. The linked cancellation
source remains explicit in the two parallel SSI jobs; extracting that ownership was discussed
but has not been implemented or implied by the rename. Existing exception-filter differences,
worker draining and job-local executeUntil budgets remain intentional.

`Core/Helpers/BackgroundJobExecutionScope.cs` follows the existing static-factory convention, with its
factories on the scope itself so its constructor can be private. The separate factory helper was
removed; ordinary C# callers, including other Domain classes, must use the named factories.
Application lifetime remains mandatory and null-checked. Create(applicationLifetime, logger: optional)
is lifecycle-only; CreateWithLock(applicationLifetime, distributedLockService, logger: optional)
supports locking. All 39 current entry points already use distributed locks and keep them through
CreateWithLock. The lock-free factory does not silently acquire/release anything, and an accidental
TryAcquireLockAsync call on that scope fails explicitly. Logging is optional in both factories;
all current jobs still pass their existing logger to retain operational warnings.
Keep these two factory names rather than separate WithLogging variants: the optional logger
already supports both modes without duplicating factory methods or changing the locking policy.

The scope centralizes the repeated plumbing, not business execution. It owns one non-retrying lock attempt, host-stop checks before
and after acquisition, shared shutdown logging/exception creation and async release of an
acquired lock. CallerMemberName captures the original job method and passes it explicitly to
the lock service, preserving existing Datadog process labels. A false acquisition still skips
the job; the existing RunWithLockAsync retry/wait behavior is deliberately not substituted.

The usage pattern is:

```csharp
await using var job = BackgroundJobExecutionScope.CreateWithLock(_applicationLifetime, _distributedLockService, _logger);

try
{
  if (!await job.TryAcquireLockAsync(lockIdentifier, lockDuration)) return;

  // At the existing safe boundary, before starting the next durable unit:
  job.ThrowIfStopping();
  // Existing provider + save / batch / snapshot logic remains here.
}
catch (Exception ex)
{
  job.ThrowIfStopping(ex);
  // Existing ordinary exception handling remains here; not stopping means this call returns.
}
// Keep the job's existing business finally blocks.
```

The exception overload logs and throws cancellation with the original cause/token only when the
host is stopping. This removes the repeated filtered catch. Do not call it from an exception
filter: CLR filters swallow their own exceptions. A using/dispose method cannot inspect the
escaping exception; moving exception conversion there could mask business/cleanup failures or
turn a completed final unit into a failure. Disposal therefore remains cleanup-only. The sync
push failed-run marker stays explicit before conversion; the download timeout catch retains its
own ordinary handling. SSI tenant/issuance retain their existing cancellation-only conversion at
the outer boundary, with fatal worker failures already wrapped before reaching that boundary.

The scope is single-owner: await lock acquisition and all started workers before leaving it.
It is not a transaction, has no Complete/rollback behavior, does not force-cancel providers and
does not drain workers automatically. Existing private helpers retain their explicit host checks;
no ambient/global job context or new helper-parameter contract was introduced. Linked SSI
dispatch cancellation still distinguishes fatal-worker stop from host shutdown. Repeated disposal
is harmless, and release is never attempted for an unacquired lock. Direct tests cover these
rules, caller labels, failure propagation and cleanup ordering, alongside the existing job tests.

## Gotchas

- Cooperative stop is not an immediate abort. A provider call, export, snapshot or document pass
  can take longer than the remaining host/pod grace period. No grace-period/server-timeout/Helm
  setting was changed here. A forced kill/OOM/node failure can still skip finally; existing Redis
  TTL, idempotent provider references and recovery remain necessary. Do not promise lock release
  after a catastrophic process death or manually clear a lock while its worker may still run.
- Unattempted items stay pending. A run may legitimately finish its last safe unit and return
  normally even if stop was signaled during that final unit; there is no artificial rollback.
- Ordinary item failures retain existing service retry handling. If the host is stopping while
  dependencies are failing, cancellation propagates without recording shutdown as a business
  error/retry. Earlier committed units remain committed; the next run handles remaining work.
- The Redis lock's existing ownership/TTL implementation is unchanged. This is not a lock-protocol
  redesign, no new distributed locks were added and no lock was manually cleared by this session.
- Catalogue memory profiling/streaming and CSV background-processing redesign remain separate.
- The old deferred local patch is now superseded by this reviewed working tree. Do not apply it
