## Education lookup expansion

The Yoma EF migration preserves the existing Tertiary Education ID (`2c0f0175-7007-40bf-9bf9-6d15b793bc09`) and renames its lookup value. Keycloak stores the user's `education` attribute as text, so the EF migration does not rename existing Keycloak values. The realm export changes also do not migrate user data or automatically update the live profile configuration of an existing realm.

| Keycloak user attribute | Exact old value | Exact new value |
| --- | --- | --- |
| `education` | `Tertiary (Diploma, Degree or equivalent)` | `Tertiary (Qualification not specified)` |

Only this exact value changes. Do not touch Primary, Secondary, No formal education, Other, null/absent values or users in other realms. The six new Tertiary choices have no existing Keycloak user rows to migrate.

For each environment independently (Stage, then Production):

1. Confirm the target Keycloak realm and live database schema. Count rows with the exact old `education` value in that realm and record the count. Back up the affected data.
2. Prepare a realm-scoped, exact-match, transactional DB update from the old value to the new value using Robbie's established Keycloak DB migration procedure. Review the SQL and rollback before execution; do not infer table or column names from this note.
3. Coordinate the DB update with applying the Yoma EF migration and updating the **live** Keycloak user-profile Education options to the eleven values in `src/keycloak/exports/02-yoma-profile.yaml`. If the changes cannot be applied together, temporarily allow both old and new Tertiary values in the live profile until the DB update completes, then remove the old option.
4. Verify the old-value count is zero, the new-value count increased by the recorded number, and an affected user's profile can be read and edited. Confirm the live Education options include the new values and exclude the old Tertiary value.

Do not run the Production update merely because Stage is complete. Repeat the count, backup, reviewed update and verification against Production at its own release.

## PostgreSQL PostGIS prerequisite — before the Yoma EF migration

This section concerns the **Yoma application database**, not the Keycloak database. Location storage for users and opportunity country mappings now uses `geography(point,4326)`. The CF migration `20260922063352_ApplicationDb_CF_Configuration` registers PostGIS using the same EF extension-annotation pattern as `pg_trgm`, before creating the spatial columns and indexes. It enables an available extension; it cannot install missing server extension files.

### Confirmed Stage preflight (2026-09-28)

Adrian supplied read-only results from `yoma_v3_stage`, connected as `yoma_v3_stage`:

- PostgreSQL 18.4; PostGIS 3.6.3 is available but not installed in this database.
- The account is not a superuser. It has CREATE privileges on the database and `public` schema.
- PostGIS reports `superuser = true`, `trusted = false`: these CREATE privileges do not meet its standard installation requirements.
- `pg_trgm` 1.6 is already installed and is trusted. Its successful installation does not establish permission to install PostGIS.
- Production and recreated Dev have **not** been checked. Do not assume they match Stage or that a different deployment account has the same privileges.

### Required rollout actions

1. Confirm the target Yoma database and actual EF migration account independently for each environment.
2. On Stage, use an authorised administrative account to enable PostGIS **before** deploying the CF migration. Repeat the availability/permissions check for Production and enable it there before its own rollout. Do not permanently elevate the application account just for this step.

   ```sql
   -- Connect to the target Yoma application database, not Keycloak.
   SELECT current_database(), current_user;
   CREATE EXTENSION IF NOT EXISTS postgis;
   ```

3. Reconnect as the EF migration account and verify the installed extension and geography type are visible:

   ```sql
   SELECT e.extname, e.extversion, n.nspname AS schema_name
   FROM pg_extension e
   JOIN pg_namespace n ON n.oid = e.extnamespace
   WHERE e.extname IN ('postgis', 'pg_trgm');

   SELECT to_regtype('geography') AS geography_type;
   ```

   Expect an installed PostGIS version and a non-null geography type. If PostGIS is installed outside the account's search path, resolve schema visibility/usage before deployment. The EF migration reuses an already enabled extension.

4. **Dev is recreated on demand:** ensure the PostgreSQL image/server includes PostGIS, and provision the extension in every newly created Yoma database before the application migration, or run that migration using an appropriately authorised account. A one-off enablement in a disposable Dev database is not sufficient. Apply the same prerequisite to fresh local databases.
5. After the EF migration, confirm its history entry and the opportunity-country spatial/text indexes. PostGIS installation alone does not prove the entire migration will succeed; rehearse the full migration on a disposable environment copy where required.

Adrian subsequently confirmed Stage and Production are fixed. No remote extension was installed by the agent. Do not drop PostGIS as a rollback step once application columns depend on it.
