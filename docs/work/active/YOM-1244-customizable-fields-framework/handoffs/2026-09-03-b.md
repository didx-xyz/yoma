### The structural change — opportunity type is MULTI-select and provenance-aware

- `DiscoveryFilters.type: string | null` → **`types: string[]`** (enum names; URL `type=Job,Event`
  via the existing list codec — an old single-value URL parses as a one-item list).
- Reducer: `setType` → **`toggleType`**. Removing a type clears ALL custom-field clauses (clauses
  are not tagged by type; clearing beats guessing which belonged to the departed type). Adding
  one orphans nothing and keeps clauses.
- `TypeRow` is multi-select and reads EFFECTIVE types; deselecting the inherited one skips the
  Goal preference — chip semantics, one behaviour everywhere. This also fixes both "inherited
  type not pre-selected" feedback items (segment popup and filters dialog are the same TypeRow).
- `TypeSpecificFilters` renders **one collapsible section per effective type**, headed
  "«DisplayName» filters" (feedback: "Job filters / Learning filters"), FROM THIS TYPE badge
  kept. Sections partition `filters.customFields` by their definition keys; generic definitions
  arrive with every type, so a generic clause shows and edits consistently in each open section.
- Ripples: `preferenceMapping` (goal fragment → `{types: [...]}`, types union in the merge),
  `chipModel`/`chipGroups` (type chips flow through `MANUAL_LIST_FACETS`), `searchRequest`
  (names → GUIDs, n types), `quickSearches` (`jobs-in-country` owns `types: ["Job"]`),
  `resolveLabel` gained a `types` case (resolves by enum NAME to displayName, not by id),
  `AppliedChips` labeler fetches definitions for all effective types.

## Gotchas

- **Any type removal clears every custom-field clause** (global rule at the top of
  `reduceDiscovery` — do not re-add per-action clearing). If per-type clause retention is ever
  wanted, clauses need a type tag (URL-format change) — flagged, not built. The master
  preferences switch is the one path that can drop a type without clearing clauses.
- Generic custom-field definitions appear inside EVERY open per-type section (the endpoint
  returns generic + type-specific per type, and definitions carry no type marker to split on).
  With one type selected — the common case — this is invisible. An API-side "which type owns
  this definition" marker would let the web split them; low priority.
- The old `?type=Job` single-value URLs still parse (list codec, one item) — recents recorded
  before this session replay correctly.
- The wizard's save now also dispatches a URL update (`resetPreferenceOverrides`); if a future
  change adds another dispatch in the same tick, remember `useDiscoveryQuery` re-parses
  `router.query` per dispatch precisely so they don't clobber.
