## Typed criteria and defaults

Ordinary criterion shape:

```json
{ "engagementTypes": { "value": ["0b2aaf7a-fdcf-4015-9668-d06bdebafa09"], "unspecified": "Include" } }
```

- `Exclude`: matching known values only.
- `Include`: matching values OR genuinely unspecified data. A known incompatible value is not unspecified.
- `Only`: unspecified data only; omit `value` completely.
- Omitted mode uses the criterion's default below. Omitted criterion does not filter.
- Empty selection arrays without a mode are normalized away. Include/Exclude require a meaningful comparison. False and zero are real values, not missing values.
- Types/Organizations/RewardTypes use the wrapper but reject **every** unspecified mode, including explicit Exclude, because these fields cannot be absent.

| Criterion | Value shape / comparison | Default | Meaning of unspecified |
| --- | --- | --- | --- |
| `provider` | String; literal case-insensitive substring | Exclude | Null provider |
| `incentivized` | Boolean, including false | Include | Null incentive flag |
| `rewardTypes` | Enum-name array; ANY | No modes | Not applicable; None is known |
| `accessibilitySupport` | Enum name | Include | Null support |
| `accommodationOtherDescription` | String; literal case-insensitive substring | Exclude | Null text on an **actual Other mapping** |
| `accommodations` | Lookup-ID array; ALL | Exclude | Empty list unless support explicitly says No |
| `targetedGroups` | Lookup-ID array; ANY | Include | Empty mapped list |
| `sustainableDevelopmentGoals` | Lookup-ID array; ANY | Include | Empty mapped list |
| `age` | Plain non-negative short; inclusive eligibility | No modes | Open age bounds are unrestricted, not unknown |
| `types` | Lookup-ID array; ANY | No modes | Type is required |
| `categories` | Lookup-ID array; ANY | Exclude | Empty mapped list |
| `languages` | Lookup-ID array; ANY | Exclude | Empty mapped list |
| `organizations` | Lookup-ID array; ANY | No modes | Owning organisation is required |
| `engagementTypes` | Lookup-ID array; ANY | Exclude | Null single Opportunity engagement |
| `skills` | Skill-ID array; ANY | Exclude | Empty mapped skill list |
| `commitmentInterval` maximum | `{ "interval": { "id": "<interval ID>", "count": 4 } }` | Include | Interval or count absent |
| `commitmentInterval` exact | `{ "options": ["4|<interval ID>"] }` | Exclude | Interval or count absent |
| `zltoReward` | `{ "ranges": ["0|100"] }` OR `{ "hasReward": true }` | Exclude | RewardType ZLTO with null amount only |
| CF clause | Existing key/operator/value shape plus `unspecified` | Exclude | Applicable definition has no stored value |

Default changes matter: manual engagement and provider selection now default to strict matches; a maximum commitment now includes unknowns while exact options remain strict. Existing incentivized/support/target/SDG inclusion defaults are retained but are explicitly overridable. Categories/languages/accommodations remain strict by default.

Explicit No accessibility is never treated as unknown accommodation support or admitted by contradictory imported/legacy mappings. A non-empty partial/incompatible list is also a known non-match, even under Include. AvailableOnRequest with an empty list is unknown suitability, not confirmed suitability.

Other-description filtering requires Other in `accommodations.value` in the **same** root/branch object. The SQL text/missing query additionally requires a real Other mapping, even if the accommodation criterion itself uses Include.

Commitment exact options and maximum are mutually exclusive. Maximum comparison normalises supported intervals to minutes using existing fixed duration conventions. ZLTO ranges and positive `hasReward` are mutually exclusive. `hasReward: false` without ranges is inactive and cannot be the sole active branch or carry an override. Zero amounts are known; None/PartnerIncentive are not unknown ZLTO rewards.

## Country-scoped search

Country selection remains a plain array, not a wrapped criterion. Countries are OR alternatives. Optional details within one country entry are AND-ed against the **same country mapping**:

```json
{
  "countries": [
    {
      "countryId": "bab77522-001d-42cb-a1ee-394e16ee5613",
      "region": { "value": "Western Cape", "unspecified": "Include" },
      "city": { "value": "Cape Town", "unspecified": "Include" }
    },
    { "countryId": "0efb07e6-6634-46de-a98d-a85bf331c20e" }
  ]
}
```

Region/city default Include. Text matching is literal, case-insensitive contains; `%`, `_` and backslash are escaped, not wildcard syntax. The shared property-contains helper is used by location and the new core text criteria.

Radius is an alternative to region/city, including when a text/radius criterion uses Only:

```json
{
  "countries": [{
    "countryId": "bab77522-001d-42cb-a1ee-394e16ee5613",
    "radius": {
      "value": { "coordinates": [18.4231, -33.9221], "radiusKm": 25 },
      "unspecified": "Exclude"
    }
  }]
}
```

Radius defaults Exclude; Only means missing coordinates in that country. Coordinates are `[longitude, latitude]`, finite and in range; radius is finite and positive kilometres. Duplicate countries and Worldwide entries with any detail criterion are invalid. Worldwide is not automatically added: Web must add it when inheriting the home country.

Country write/response models remain flat (`countryId`, region, city, coordinates); this is a **search-only** nesting change. PostGIS storage and existing GiST/trigram indexes remain in use; no client-side radius fallback or new spatial migration is needed.

## OR groups and mandatory scope

```json
{
  "totalCountOnly": true,
  "groups": [{
    "anyOf": [
      { "types": { "value": ["d74da423-7779-4f49-9d6b-92ce5f61f4a1"] } },
      { "categories": { "value": ["c76786fd-fca9-4633-85b3-11e53486d708"] } }
    ]
  }]
}
```

This example is Entrepreneurship type **OR** Business, Finance & Marketing category, not a hardcoded API goal rule.

Evaluation is `mandatory scope AND root criteria AND (group 1 alternatives) AND (group 2 alternatives) ...`. Each branch's members are AND-ed. Root and branch repetitions add constraints; they do not overwrite one another.

- Maximum 4 groups; 8 branches per group; 24 active criteria per branch.
- No empty group/branch or recursive nesting.
- Paging, ordering, status/date/public-state controls, Featured, ShareWithPartners and cross-field ValueContains are root-only.
- Unknown root/branch members are rejected, not silently ignored.
- Permission, owning-organisation, visibility and public-state constraints stay outside every group. An empty authorised organisation list means zero results.
- SQL ID subqueries/Union implement alternatives; count, sort and paging remain database-side. Hydration retains the non-text constraints and restores selected page order.

## CF applicability

The API hydrates the active definition's `entityContext` and resolves its type ID before repository filtering:

- Null context: applies to all types.
- Type context: constrains that type only; other types pass unchanged, not as missing records.
- Applicable records follow match/unknown mode semantics.
- Same rules at root/in branches and youth/admin.
- Select the type separately for an admin gap query that should return only that type.

Only uses `{ "key": "jobSalaryMinimum", "unspecified": "Only" }` with no operator or values. Other operators retain their existing type/shape validation. Exists checks actual presence, uses no values and rejects Include/Only; explicit Exclude or omitted mode are allowed. Duplicate CF keys in one selection are invalid.

Absent salary amounts remain generically absent, even when Salary disclosed is false; the disclosed flag is a known false. No salary-specific exception or preference mapper is embedded in the missing-value engine.

## Ordering, counts and published dates

```json
{
  "pageNumber": 1,
  "pageSize": 12,
  "ordering": [{ "field": "DateEnd", "direction": "Ascending" }]
}
```

Public sort fields: DateCreated, DateEnd, ZltoReward. Directions: Ascending/Descending. One to three unique fields, in order; unknowns/duplicates are invalid. Nullable fields are last in either direction; ID ascending is always the final tie-break. Internal expressions remain hidden.

Omitted ordering retains youth DateStart descending, DateEnd ascending/null-last, Title ascending, ID ascending; admin DateCreated descending, ID ascending. Explicit ordering cannot be combined with active MostViewed/MostCompleted. Popularity remains mutually exclusive and preserves its existing rank; an empty popularity set safely returns no results.

Only a root incentive criterion with a real true/false value and resolved Include creates two buckets: explicit matching flag first, unknown flag second, then selected/default ordering inside the bucket. Exclude/Only/branch-only incentives and other criteria do not create ranking buckets.

`totalCountOnly: true` is public on both searches. It uses the identical filtered/authorised query, returns `totalCount` with `items` unpopulated, and does not require page fields or load children/treasury/engagement counts. No batched endpoint: send one count request per effective combination. CSV export rejects count-only.

One captured UTC instant per query governs dates:

- NotStarted: Active status, future start, no already-past end.
- Active: Active status, start reached, end absent or not yet past.
- Expired: Expired status OR Active status with already-past end.
- End exactly at now remains Active, not Expired.

Public results still require an Active organisation and existing visibility rules. Filtered reference-list shapes are unchanged, but their Active/Expired contents now follow these same date rules. Verification/finalisation rules are separate from public discovery state.

## Engagement preferences and migration

PATCH uses `engagementTypes: [<lookup IDs>]`. GET/PATCH response uses `engagementTypes: [{ id, name, displayName }]`, ordered by display name. Singular `engagementTypeId`/`engagementType` preference fields are removed. Opportunity engagement stays single-select. Remote + On-site and any other valid combination are accepted; IDs are validated and duplicates removed.

PATCH is still **complete replacement of all preferences**. Send the complete model; omitted/null/empty selections clear them, not preserve them. A failed validation leaves all previous selections intact. User/profile responses remain separate and Keycloak is unaffected.

New migration `ApplicationDb_UserPreference_EngagementTypes`:

1. Create `Entity.UserPreferenceEngagementTypes`, with NoAction FKs to UserPreferences and EngagementType.
2. Unique `(UserId, EngagementTypeId)` plus reverse lookup index.
3. Copy each old non-null EngagementTypeId to one mapped selection, preserving its creation date.
4. Drop the old FK/index/scalar column. Empty choices remain empty.

Down throws a generic loss-of-preferences exception: multi-select cannot safely downgrade to one selection. The upgrade test migrates a fresh pre-CF schema forward, verifies the retained choice/empty case, and confirms no pending EF model changes.

### Capture-path requiredness — unchanged framework policy

`isRequired` describes the manual capture requirement; it is not a universal ingestion constraint. Search missing-value policies do not change write validation or make absent external CF data invalid.

| Capture path | Required CF enforcement | Supplied values |
| --- | --- | --- |
| Manual Opportunity create/update by an admin | Enforced (`PutEnforceRequired`) | Validated; complete replacement |
| Manual youth submission for completion | Enforced (`PutEnforceRequired`) | Validated; complete replacement |
| Partner-synced Opportunity or completion | Not enforced (`PatchAllowMissingRequired`) | Validated when supplied; omissions preserve existing values |
| Opportunity or completion CSV import | Not enforced (`PatchAllowMissingRequired`) | Validated when populated; omitted columns preserve values and blank cells clear them |
| Instant/action-link completion | Not enforced (`None`) | CF processing deliberately skipped |

Conditional companion requirements follow the same boundary. Manual selection of Other requires its description. Sync/CSV may supply Other without text, or text while the selection is unspecified; known non-Other selections with Other text remain contradictory. Salary and employment rules already distinguish missing external companions from contradictory supplied facts. No seeded required flags or capture modes were changed by the search revision or this clarification.

Job placement submissions may omit participation start and commitment; supplied values must still be coherent. Advertised effort no longer fabricates participation timing. `jobEmploymentStartDate` remains a separate optional completion CF; historical records are not rewritten.

The Pending admin search, related Opportunity picker and aggregate pending counts now gate on **OpportunityDateStart**, not nullable youth DateStart. This is essential for reviewing Job/Entrepreneurship submissions without participation dates. Evidence, auth, CF checks, submission eligibility and the no-Job-skill-award rule remain intact.
