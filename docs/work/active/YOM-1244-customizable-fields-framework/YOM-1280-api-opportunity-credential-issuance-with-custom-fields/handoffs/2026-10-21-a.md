## Per-Item Recovery Contract

1. A deliberately scoped future migration marks a retained schedule **Replay** after old workers are paused/drained. Preserve its client referent, credential ID, schema name/version, artifact/entity references and date.
2. Resolve the existing holder and validate the old artifact against holder, ID, client referent and schema/artifact type. Persist the identity/date checkpoint **before deletion**.
3. Delete through the current provider and confirm absence by ID and client referent. The provider commits its own storage; no ambient transaction spans provider and Yoma stores.
4. Commit a single schedule update to **Pending**, clearing `CredentialId`, `SchemaVersion`, `ErrorReason` and `RetryCount`, retaining `DateIssued`. If deletion succeeds but this save fails, Replay remains durable; the next run confirms absence and completes the reset. Cleanup failures never enter ordinary issuance's error-to-Pending policy.
5. Once all cleanup succeeds, normal tenant-ready issuance resolves the latest version of the committed schema name. Success becomes **Issued**, recording actual credential identity/version/date. Ordinary provider-success/local-save recovery remains referent-based and does not delete the replacement.

Tenants remain Created, with the same holder/issuer IDs, connections, schemas and provider mappings. No completion, reward or referral actions are replayed.

## Gotchas

- Queue reset alone can recover the old credential by client referent; wallet reads do not hide artifacts because queue status changed. Only Replay authorizes deletion.
- Pending with a retained credential ID may represent ordinary provider-success/local-save recovery, not cleanup. Reconcile it before including it in a future Replay migration.
- Provider deletion may succeed before the domain save fails. Retained Replay identity/date is the recovery checkpoint. Do not couple provider/Yoma connections or enable distributed transactions to hide this boundary.
- A failed Replay row blocks Pending dispatch by design; fix its recorded cleanup error and retry the existing job.
- Legacy DateModified backfill is an explicitly approved approximation. Runtime never substitutes audit timestamps for missing original dates. Replacement signatures/provider creation timestamps are current even when the Yoma date claim is historical.
- Wallet deletion does not revoke exported copies. Never delete unrelated credentials or infer tenant deletion cascades.
- Provider switching remains a separate one-way DI/deployment plus data-preparation migration. Preserve dates/scheduling commitments, reset domain/provider mappings for the new provider, and let SRE retire the old provider. No old-provider cleanup mode is implemented.
