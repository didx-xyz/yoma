## What Was Done

Extended the existing country mapping rather than renaming Countries to Locations. One country mapping per opportunity holds optional region, city and coordinates; multiple countries remain supported. Existing country IDs and associations remain intact, with new details null. This is core data, not CF configuration. No web code was changed.

## UI contract for Jason

All routes below use `/api/v3`. This is a breaking country-request shape change; do not send the former GUID array to create/update, assign, or ordinary opportunity search.

### Capture and readback

- Opportunity create/update uses `countries: [{ countryId, region, city, coordinates }]`. `OpportunityRequestCountry` is the request model; there is no separate locations collection or location endpoint.
- `PATCH /opportunity/{id}/assign/countries` accepts that array directly. It adds/updates the supplied countries, preserving unlisted mappings. Optional details on each supplied country are replaced; omitted/null details clear them. Returns the existing empty HTTP 200 response; reload the opportunity afterward.
- Full opportunity update replaces the country selection, removing unlisted countries. Preserve loaded details during unrelated edits.
- `PATCH /opportunity/{id}/remove/countries` remains an array of country GUIDs.
- Country is required, unique per opportunity. Region/city are optional, maximum 255 characters each. Worldwide cannot carry region, city or coordinates.
- Coordinates are nullable `[longitude, latitude]`, exactly two finite in-range numbers, with no elevation. Radius is not stored.
- Opportunity, item and info responses expose `countries` with `id`, `name`, country codes, `region`, `city`, `coordinates`. Response `id` is the country lookup ID, not the mapping ID; map it to request `countryId` when editing. `OpportunityCountryInfo` extends the existing Country response.
- Country lookup: `GET /lookup/country`. Opportunity pickers may include Worldwide; profile pickers still exclude it.

### Discovery search

Both `POST /opportunity/search` and `POST /opportunity/search/admin` now accept:

```json
{
  "pageNumber": 1,
  "pageSize": 10,
  "countries": [
    {
      "countryId": "bab77522-001d-42cb-a1ee-394e16ee5613",
      "region": "western",
      "city": "cape"
    }
  ]
}
```

- Country entries are independent alternatives (OR), preserving the previous country-list semantics. Optional criteria apply only to that country's mapping. Region AND city must match that same mapping, not separate countries on an opportunity.
- Text uses case-insensitive contains. Null region/city remains included independently, to retain incomplete partner data. Wildcard handling is unchanged from existing repository Contains behaviour.
- Alternatively send `coordinates: [18.4231, -33.9221], radiusKm: 25` in that country entry, with no region/city. Coordinates and positive finite radius must come together. Combining text with radius is rejected, not silently ignored.
- Radius excludes unknown coordinates and evaluates on the database before counting/paging. Do not apply client-side distance filtering to a paged result.
- Country-only entries are valid; duplicate country entries are rejected. There are no top-level region/city/radius fields.
- The separate criteria/quick-picker contract (`OpportunitySearchFilterCriteria`) retains its GUID country list. Do not mechanically change every `countries` payload in web.
- Jason's component object `{ latitude, longitude }` must be converted to `[longitude, latitude]`. Existing UI radius choices can be sent in kilometres. Enable `LOCATION_SEARCH_LIVE` only after wiring this final nested contract; the prototype's flat search assumptions are superseded.
- This does not implement saved-preference-to-search mappings or automatically apply the profile location. Those remain separate work.

## User location alignment

User profile payloads and endpoints are unchanged. Storage changed from the earlier planned JSONB column to nullable PostGIS `geography(point,4326)`, matching opportunity coordinates. The wire representation remains the same array; no location wrapper, second country ID, radius or provider place ID was introduced. Shared coordinate validation is reused. User coordinates remain city-centre coordinates, not a precise device fix, and location remains Yoma-only (not Keycloak or UserPreferences).

## CSV and partner sync

- CSV remains country codes only; no manually entered location columns were added. Imports preserve existing details for retained countries; new mappings start unspecified. Exports remain country-only.
- JobJack maps Province to Region and City to City. Its existing company/city title distinction is retained to distinguish placements. Its free-form Location remains in the description: embedded payloads include mall/street detail not represented by structured city/province. No geocoding or parsing of free-form locations.
- Other audited pull partners supply country-only objects. Raw partner sample payloads were not changed.
- Existing push-sync country guards still protect required country membership (e.g. SA Youth requires ZA). They intentionally compare country IDs, not region/city. Pull-managed opportunities remain protected against local edits.
