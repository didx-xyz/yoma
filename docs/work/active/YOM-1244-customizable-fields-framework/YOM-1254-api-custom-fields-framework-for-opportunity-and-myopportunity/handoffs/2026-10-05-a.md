### Guidance Labels and Tooltips

For the youth-facing details/search UI:

- **Difficulty** describes readiness/complexity; do not label it as a permission to apply or complete.
- **Experience level** communicates the advertised experience expectation. The API does not compare it with the youth's employment history or self-attested skills.
- **Minimum qualification** communicates the provider's formal qualification expectation. The API does not compare it with the profile Education field to reject a submission. Its existing definition description explicitly says it is informational and searchable, not an automatic eligibility gate.
- **Preferred skills** are bonus skills, not compulsory matches and not verified skills awarded for a Job placement.

A missing description is not an implied eligibility rule. The provider may assess suitability separately. The existing age-on-submission rule is a distinct, explicit API gate; these CFs do not replace it.

## Selected Skill Lookup Contract

Dedicated anonymous, read-only lookup endpoint:

```http
POST /api/v3/lookup/skill/ids
Content-Type: application/json

[
  "01a0e88e-a2ee-7b30-954f-8117e6e57e92",
  "01a0e88e-a423-7394-97b9-84f1e6213f9d"
]
```

- Body is the JSON array itself, **not** `{ "ids": [...] }`. It must contain at least one non-empty GUID. There is no application-level ID-count limit; the initial 1,000-ID cap was removed at Adrian's request. Skip the request when there are no selected values to resolve.
- Returns **all known matches**, ordered Name → Id, as a plain `[{ id, name, infoURL }]` list. There is no `totalCount`/`items` wrapper, pagination or name filter on direct lookup.
- Duplicate IDs return each skill once. Valid but unknown IDs return no item; an entirely unknown selection returns HTTP 200 with `[]`. Unknown IDs are not name aliases. Missing/retired references can retain the UI's explicit fallback rather than being assigned another label.
- Invalid/empty GUIDs, empty/null/missing JSON bodies and incorrect body shape return HTTP 400. Requests without a supported JSON content type follow standard ASP.NET Core HTTP 415 behavior.
- POST keeps selected-ID resolution independent of query-URL length limits; it does not mutate data. Supply all selected IDs in one request; no count-based chunking is required. Normal server/proxy request-body safeguards remain unchanged.
- The domain uses an injected shared `LookupIdsValidator` and the existing cached catalogue/read path, with a HashSet membership check. No external catalogue-provider call is made per ID.
- **Existing search is unchanged:** `GET /api/v3/lookup/skill?nameContains=python&pageNumber=1&pageSize=10` still returns `{ totalCount, items }`, requires valid paging, and also supports paged browsing when name is omitted. `SkillSearchFilter` has no IDs member. Do not use the earlier selected-ID query proposal.

Jason: use this for lookup-backed `Skill` CF read-only rendering and any selected-value editor hydration that currently relies on page 1. Keep ordinary text autocomplete as ordinary paged name search. Inline CF options still bind to **option keys**; lookup-backed options bind to **lookup IDs**; labels are presentation only. Neither values nor filter payloads should switch to display names.

#### Read-Only Preflight — Each Shared Yoma Database

Run as the actual application migration account on Dev, Stage and Production independently. This query is safe before CF is deployed and does not install an extension or alter data:

```sql
BEGIN READ ONLY;
SET LOCAL statement_timeout = '15s';

SELECT current_database() AS "Database", current_user AS "Account", version() AS "Version",
    r.rolsuper AS "IsSuperuser",
    has_database_privilege(current_user, current_database(), 'CREATE') AS "CanCreateInDatabase"
FROM pg_roles r WHERE r.rolname = current_user;

SELECT wanted.name AS "Extension", a.default_version AS "AvailableVersion",
    a.installed_version AS "InstalledVersion", v.superuser AS "RequiresSuperuser", v.trusted AS "Trusted"
FROM (VALUES ('postgis'), ('pg_trgm')) AS wanted(name)
LEFT JOIN pg_available_extensions a ON a.name = wanted.name
LEFT JOIN pg_available_extension_versions v ON v.name = a.name AND v.version = a.default_version;

SELECT to_regtype('geography') AS "VisibleGeographyType";

SELECT "MigrationId" FROM "__EFMigrationsHistory" ORDER BY "MigrationId" DESC LIMIT 5;

SELECT table_schema, table_name, column_name, udt_name
FROM information_schema.columns
WHERE (table_schema, table_name) IN (('Opportunity', 'OpportunityCountries'), ('Entity', 'User'))
    AND column_name IN ('Region', 'City', 'Coordinates', 'LocationSource')
ORDER BY table_schema, table_name, column_name;

ROLLBACK;
```

Expect installed/visible PostGIS when rehearsing deployment. CREATE permission alone does not authorise an untrusted PostGIS installation. Missing new columns on a not-yet-deployed environment are expected; do not run the next audit until the CF schema exists.

#### Read-Only Coverage Audit — After the CF Migration

This reports facts for release/discovery decisions; it does not infer city points, set incentives or backfill missing metadata. The location totals count country mappings, not distinct Opportunities: an Opportunity can have more than one country.

```sql
BEGIN READ ONLY;
SET LOCAL statement_timeout = '15s';

SELECT t."Name" AS "Type", c."CodeAlpha2" AS "Country", COUNT(*) AS "CountryMappings",
    COUNT(*) FILTER (WHERE oc."Region" IS NOT NULL) AS "WithRegion",
    COUNT(*) FILTER (WHERE oc."City" IS NOT NULL) AS "WithCity",
    COUNT(*) FILTER (WHERE oc."Coordinates" IS NOT NULL) AS "WithCoordinates"
FROM "Opportunity"."OpportunityCountries" oc
JOIN "Opportunity"."Opportunity" o ON o."Id" = oc."OpportunityId"
JOIN "Opportunity"."OpportunityType" t ON t."Id" = o."TypeId"
JOIN "Opportunity"."OpportunityStatus" s ON s."Id" = o."StatusId"
JOIN "Lookup"."Country" c ON c."Id" = oc."CountryId"
WHERE s."Name" = 'Active' AND o."DateStart" <= CURRENT_TIMESTAMP
    AND (o."DateEnd" IS NULL OR o."DateEnd" >= CURRENT_TIMESTAMP)
    AND NOT o."Hidden"
GROUP BY t."Name", c."CodeAlpha2"
ORDER BY t."Name", c."CodeAlpha2";

SELECT t."Name" AS "Type", COUNT(*) AS "Opportunities",
    COUNT(*) FILTER (WHERE o."Incentivized" IS NULL) AS "UnspecifiedIncentive",
    COUNT(*) FILTER (WHERE o."AccessibilitySupport" IS NULL) AS "UnspecifiedAccessibility"
FROM "Opportunity"."Opportunity" o
JOIN "Opportunity"."OpportunityType" t ON t."Id" = o."TypeId"
JOIN "Opportunity"."OpportunityStatus" s ON s."Id" = o."StatusId"
WHERE s."Name" = 'Active' AND o."DateStart" <= CURRENT_TIMESTAMP
    AND (o."DateEnd" IS NULL OR o."DateEnd" >= CURRENT_TIMESTAMP)
    AND NOT o."Hidden"
GROUP BY t."Name" ORDER BY t."Name";

SELECT "EntityType", "EntityContext", "Group", "SubGroup", COUNT(*) AS "Definitions"
FROM "Core"."CustomFieldDefinition" WHERE "IsActive"
GROUP BY "EntityType", "EntityContext", "Group", "SubGroup"
ORDER BY "EntityType", "EntityContext", "Group", "SubGroup";

SELECT schemaname, tablename, indexname, indexdef FROM pg_indexes
WHERE (schemaname, tablename) IN (('Opportunity', 'OpportunityCountries'), ('Core', 'CustomFieldValue'))
ORDER BY schemaname, tablename, indexname;

ROLLBACK;
```

These availability aggregates intentionally are not a clone of an authorised Opportunity search (organisation visibility, the consumer's filters and published-state choices can reduce it further). They are a deployment/data audit, not a promised UI result count.
