## What Was Done

- Adrian confirmed that Jason's Web discovery flow owns preference inheritance, per-preference skips and manual overrides. It sends the resulting ordinary search criteria. The API does not read preferences or perform a second mapping. The inert `ApplyUserPresets` request field, validator restriction and exception were removed.
- Exposed `totalCountOnly` on the public `POST /api/v3/opportunity/search` request. With `true`, the existing SQL search predicates return `totalCount` without loading items. `items` is null/absent; pagination is optional. With `false` or omitted, the paginated response is unchanged. Core and custom-field filters are accepted together in either mode. The count-only path also skips treasury and engagement-count enrichment.
- Audited the active prototype facets against the public filter. Type, category, language, country/location, owning organisation, engagement, commitment, ZLTO reward, text and custom-field criteria are supported by the API. The Web request builder must align the changed country/location shape; the API does not need another filter for these active facets.
- Documented the decision in the epic and API feature docs. No database migration or Web source change was needed.

## Jason's Integration Contract

1. Build the effective filter request on Web from saved preferences plus any manual selections, skips and overrides. Do not send `ApplyUserPresets`; it no longer exists. The API receives only the final criteria and performs the database filtering.
2. For the live count, send the **same effective criteria** as the results request with `totalCountOnly: true`. Read `totalCount`; do not expect `items`. Do not send pagination unless useful to a shared request builder. The ordinary results request omits the flag or sets it to `false` and supplies pagination.
3. The checked-in prototype still requests one item for its live count. Its request builder sends country GUIDs, while the current API requires `countries: [{ countryId, region?, city?, coordinates?, radiusKm? }]`. Region/city and point/radius currently remain unsent by the prototype. Coordinates are `[longitude, latitude]`; radius is kilometres. Jason is aligning these shapes.
4. The prototype's preference model/mapping still has pre-API names and values, including `Task` rather than `ImpactAction`, multi-select engagement instead of the saved single-select, and a location under preferences rather than the profile's country/region/city/coordinates. Align against the live preference/profile responses before enabling inheritance. Its `providers` facet currently filters owning organisation IDs; the new free-text `provider` field is a separate API criterion.
5. The prototype intentionally leaves skills, accessibility and some identity-derived preferences pending. The API now exposes age, accommodations, targeting, incentive, provider and CF criteria, but the UI must explicitly map any preference it chooses to use. Do not silently claim these pending rows are already active.
