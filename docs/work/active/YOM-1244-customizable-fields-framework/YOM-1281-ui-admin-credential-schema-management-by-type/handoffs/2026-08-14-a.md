### Fixes from the first browser pass (same session)

- **Attributes step is one `Data Source | Attribute` table.** It was two blocks: a read-only
  "System attributes" table above an "Additional attributes" repeater. Now one table — read-only
  core rows for the system statics (lock icon, no controls), then one row per additional attribute
  with a Datasource dropdown and an Attribute dropdown and a remove button, with add below. Both
  headers are gone.

  A grouped-checkbox rewrite was tried first and **rejected** — the two-column dropdown table is
  the shape this surface keeps. Group/SubGroup metadata therefore rides in the Attribute dropdown's
  **optgroups** (`Group › SubGroup`, straight from the API) in API order, which is how the ticket's
  "render dynamically using API-provided grouping and ordering metadata" requirement is satisfied
  without a third column. An attribute already used by another row is filtered out of the
  dropdown. Core rows are still excluded from the submitted list — the API prefixes them itself.

- **Fixed a bogus "Schema name cannot contain the characters | or :" on edit.** The new create-time
  name rule was applied to both flows, but on edit the form's `name` **is** the full provider name
  (`Opportunity|Job|test1`) because that is what `PATCH /ssi/schema` takes — so the rule fired on
  every existing schema, and the error rendered under the field showing the friendly name (`test1`).
  The refine is now applied only when `isCreate`. This blocked the edit flow at step 1 entirely.

- **Fixed: the Opportunity Type could never be cleared back to generic.** `onSubmitStep` merged it
  with `data.typeContext ?? formData.typeContext ?? null`, so the deliberate `null` from choosing
  "Generic — all opportunity types" fell straight back to the previous selection. Picking `Job` and
  then switching to generic left `typeContext: "Job"` in the discovery query key, the review step
  and the create request — so the schema was created as `Opportunity|Job|Name`. Now the key's
  _presence_ decides: `("typeContext" in data ? data.typeContext : formData.typeContext) ?? null`,
  since only the step-1 submit carries the key (zod strips it from the other steps' payloads).
  Surfaced by the attributes-step hint not updating.

- The attributes-step hint is now one static line, "Attributes available for this schema /
  opportunity type."

## Gotchas

- **A retired mapping cannot be carried forward.** `SSISchemaService.Update` validates the
  submitted attributes against `_ssiSchemaEntityService.List(type, typeContext)` — _active,
  in-context_ only — while the schema itself is rendered from `ListAll(activeOnly: false)`. So a
  custom field that is deactivated after being mapped shows on the schema but is rejected if
  resubmitted. The UI therefore shows it read-only and drops it on save. If the API later grows a
  "preserve existing mappings" rule, this block should become selectable instead.
- **The mock skips SSR prefetching** on both pages. It has to: the store lives in the browser, and
  `react-query-config` sets `staleTime` to an hour, so a server-hydrated copy would never refetch
  and created schemas would never appear. Removing the guards restores the original behaviour.
- **Mock state is in-memory and per page load.** A full browser reload resets to the four fixtures.
- `useOpportunityMutations.useOpportunitySchemasQuery` still calls the **real** `getSchemas` — it
  belongs to YOM-1282, not this feature, and was left on the live service deliberately.
- `SSISchema.type` and `artifactType` arrive as enum **names** (`"Opportunity"`, `"ACR"`), not
  ordinals. The old `ArtifactType[schema.artifactType]` lookup silently yielded `undefined` for
  AnonCreds; that is why the enum member was renamed.
- Schema full names contain `|`. Links are URL-encoded now; the `[id]` route still wins over the
  `[[...query]]` catch-all because it is a single segment.
- Type context resolves against the Opportunity Type **`Name`**, never the editable `DisplayName` —
  the selector submits `name` and displays `displayName`.
- **On edit, the form's `name` is the full provider name, not the friendly one.** `PATCH /ssi/schema`
  identifies the schema by full name, while the disabled input shows `displayName`. Any validation
  added to that field must be scoped to `isCreate`, or it will judge a value the user cannot see —
  that is exactly what the `|`/`:` rule did.
- The **Review** step (create only) is also a single `Datasource | Attribute` table now, system
  attributes marked with a lock and the chosen ones below, matching the attributes step.
- The attributes step deliberately keeps the **two-column dropdown table**. A grouped-checkbox
  version was built and rejected; do not "improve" it back into a checkbox tree. Grouping and
  ordering metadata belongs in the Attribute dropdown's optgroups.
- **Presentation metadata is not part of the signed schema.** Group/SubGroup/SortOrder are
  developer-controlled (migrations for statics, custom-field config for the rest) and read-only to
  schema admins — the UI displays them and must never submit them.
- The client-side presentation comparator in `SchemaAttributesEdit` duplicates
  `SSIAttributePresentationHelper.Order`. It exists only because discovery returns `properties[]`
  and `customFields[]` as two separately-ordered arrays that have to be merged into one dropdown.
  If the API ever returns them pre-merged, delete the comparator rather than keeping two copies of
  the rule.
