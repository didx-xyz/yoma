## What Was Done

- Reused `Entity.UserSkills` rather than adding a separate UserPreset entity. New `Type` is `UserSkillType.SelfAttested` or `Verified`; the consolidated CF migration backfills all existing rows as `Verified` and preserves their IDs and awarding-organisation associations.
- Added non-null `DateModified` to UserSkills. The migration copies each existing row's `DateCreated`; repository create sets both timestamps together, and update refreshes `DateModified` following existing User repository patterns.
- Added self-service `GET /api/v3/user/preferences` and `PATCH /api/v3/user/preferences`. Authentication supplies the user identity; no user ID is accepted in the route or request. No new preferences data is sent to Keycloak.
- The PATCH body is the **complete** current preferences model: `goalId`, `commitmentIntervalId`, `commitmentIntervalCount`, `engagementTypeId`, `incentivized`, `categories`, `accessibilityRequirements`, `accessibilityRequirementOtherDescription`, `languages` and `skillsSelfAttested` are all replaced together. Missing or null scalar choices clear them; commitment interval and count must both be supplied or both null; missing, null or empty lists clear them. Accessibility Other requires a description (up to 500 characters); without Other, omit/clear it. Duplicate IDs are deduplicated. Supplied IDs must exist, and an already verified skill cannot be submitted as self-attested.
- Both GET and PATCH return the full `UserPreferences`, including nullable `goalId` and `goal` (human-readable name) and `skillsSelfAttested` as skill objects (`id`, `name`, `infoURL`). The frequently loaded and UI-cached `GET /api/v3/user` profile and admin User response do not embed preferences. `GET /api/v3/user/skills` returns the name-ordered skill collection with each skill's `type` (`SelfAttested` or `Verified`), optionally filtered using `?type=Verified` or `?type=SelfAttested`; no filter returns both.
- Moved scalar choices from proposed User columns into one `Entity.UserPreferences` row keyed and foreign-keyed by `UserId`. Its three multi-select link tables are `Entity.UserPreferenceCategories`, `Entity.UserPreferenceAccessibilityRequirements` and `Entity.UserPreferenceLanguages`; each points to UserPreferences and its canonical lookup. Existing users have no preference row; GET returns empty defaults and the first PATCH creates it. `UserSkills` remains separate.
- Renamed the category-link domain model, EF entity and repository to `UserPreferenceCategory` for the new ownership boundary. The physical table remains `Entity.UserPreferenceCategories`; no additional schema change or API rename is involved.
- The repository parses the stored skill type string into the API enum. The `/user/skills` endpoint loads one user's existing skill collection and applies its optional type filter in memory; it does not add another database read. A raw-string projection is unnecessary until a real database-side type filter is needed.
- The profile service owns the full-update transaction and execution strategy. It calculates self-attested removals, then invokes separate UserService remove/assign methods, consistent with the opportunity update pattern. Category operations are named `AssignPreferenceCategories` and `RemovePreferenceCategories` to distinguish them from Opportunity category management.
- `GetPreferences` projects self-attested skills inline; the one-use `WithSkillsSelfAttested` extension was removed. PATCH assigns scalars and calls Create/Update without a manual change gate, as Opportunity update does. It then reloads the committed preferences because link and skill writers do not maintain the projected domain collections in memory; the response needs the current lookup details and verified-skill precedence.
- Verified opportunity completion promotes an existing self-attested UserSkill row to Verified and adds the awarding organisation. A later award from another organisation keeps the same row and adds another organisation.
- Job opportunities retain their required skills, but completing a Job does not award or promote them to Verified. The central UserService skill-assignment method skips Jobs, with an explanatory code comment and focused regression test. This rule needs a separate Production hotfix before the broader CF branch ships.
- UserService selects only self-attested rows for removal. UserSkillRepository also makes deletion conditional on the database row still being `SelfAttested`, preventing a concurrent promotion from being deleted after the service's earlier check.
- The mapping is explicitly **unverified self-assertion**. It is not a credential, an award, or a new SSI issuance flow.
- Added `Categories` as an optional multi-select preference using the existing Opportunity Category lookup. The complete PATCH replaces both category and self-attested-skill selections; null/missing/empty clears each. The response returns selected category objects. Preference-to-opportunity filtering is a separate ticket.
- Added optional single-select User Goal with nullable `UserPreferences.GoalId` and a controlled `Entity.UserGoal` lookup. Five sentence-case names are seeded: Get a job, Learn new skills, Start a business, Volunteer / make an impact, and Attend events. No DisplayName or Goal enum. Existing users are unspecified; Goal is not synchronized to Keycloak or issued as a credential.
- Added optional maximum time commitment on UserPreferences using the Opportunity field shape: nullable `CommitmentIntervalId` (FK to `Lookup.TimeInterval`) plus nullable `CommitmentIntervalCount` (`short`/smallint). The read response also includes `CommitmentInterval` using the Minute/Hour/Day/Week/Month enum. Both request fields must be present or absent and count positive. No preference-to-Opportunity filtering was added.
- Added shared `Lookup.Accessibility` with 16 approved sentence-case values, including Flexible hours and Other. An anonymous reference endpoint returns the whole list with Other last. Preferences store selected IDs through preference-owned links and optional `AccessibilityRequirementOtherDescription` (up to 500 characters) on UserPreferences. Description is accepted only with Other. No existing-user backfill, Keycloak/credential field, Opportunity CF, matching or provider disclosure. Per-application sharing remains separate consent work.
- Naming was simplified before release: shared model/service/table `Accessibility`, youth field `AccessibilityRequirements`, link model `UserPreferenceAccessibilityRequirement`, and lookup route `/api/v3/lookup/accessibility`. The previous Accommodation/Needs names are not part of the API contract.
- Standardised the shared Engagement Type lookup for all Opportunities: the existing Online and Offline rows retain their IDs while their keys become `Remote` and `OnSite`; Hybrid retains its ID/key. Added `DisplayName` to all three (`Remote`, `On-site`, `Hybrid`) for UI labels. CSV export and import both use the canonical `Name` (`Remote`, `OnSite`, `Hybrid`); the display label and legacy `Online`/`Offline` values are not CSV aliases. IXO and Umuzi each declare a partner-specific wire mapping from `Online`→`Remote` and `Offline`→`OnSite` before resolving the canonical lookup; absent values default to `Remote` and unknown values fail. Alison has a fixed Remote mapping rather than an incoming engagement value. User preferences store one nullable `EngagementTypeId` FK; no separate work-engagement custom field or automatic matching was added.
- Added nullable `Incentivized` to UserPreferences and the complete GET/PATCH. True prefers an Opportunity with any incentive; false prefers none; null means no preference. This is not Job-specific or a reward-type selector. Opportunity-side `IsIncentivized` and ranking are later work.
- Added optional `Languages` using the existing `Lookup.Language`. GET returns selected language objects; PATCH accepts their IDs and replaces the complete selection. No new language lookup, Keycloak field, credential field or matching logic was added.
- User Preferences are Yoma-owned and do not change partner-sync payloads or mappings. The only partner-sync touchpoints in this work are the shared Engagement Type lookup rename, explicit partner wire mappings and defaults. Partner sample resources retain the partners' original `Online` value.

### Read and save contract

- Open the editor with authenticated `GET /api/v3/user/preferences`. It returns the **full** `UserPreferences`: nullable `goalId` and `goal` (name), `commitmentIntervalId`, `commitmentInterval` (enum), `commitmentIntervalCount`, `engagementTypeId`, `engagementType` (enum key) and `incentivized`; `categories` is an array of category objects (`id`, `name`, `imageURL`, nullable `count`); `accessibilityRequirements` is an array of accessibility option objects (`id`, `name`), `accessibilityRequirementOtherDescription` is nullable; `languages` is an array of language objects (`id`, `name`, `codeAlpha2`); `skillsSelfAttested` is an array of skill objects (`id`, `name`, `infoURL`). A user who has never saved preferences gets null scalars and empty arrays. Use these to preselect controls; PATCH uses lookup IDs.
- Save with authenticated `PATCH /api/v3/user/preferences`, sending the **complete current selection** for every field, for example:

  ```json
  {
    "goalId": "<goal-guid>",
    "commitmentIntervalId": "<time-interval-guid>",
    "commitmentIntervalCount": 4,
    "engagementTypeId": "<engagement-type-guid>",
    "incentivized": true,
    "categories": ["<category-guid>"],
    "accessibilityRequirements": ["<accessibility-guid>"],
    "accessibilityRequirementOtherDescription": null,
    "languages": ["<language-guid>"],
    "skillsSelfAttested": ["<skill-guid>"]
  }
  ```

  A missing or `null` `goalId` clears the Goal; missing or `null` `incentivized` clears that preference, while explicit `false` means no incentive is preferred. Both commitment fields must be present with a valid interval and positive count or both be null; a missing, `null` or empty array clears that selection. When saving one wizard step, preserve the other fields from the loaded preferences (or save once at the end); omission is not a partial-update instruction. The API validates every ID against its lookup and deduplicates repeated IDs. It returns the full updated preferences; use that response to refresh local state. This endpoint is separate from profile PATCH and does not write to Keycloak.
- `GET /api/v3/user` remains the existing profile contract, with no preferences and no `includePreferences` flag. Fetch `GET /api/v3/user/preferences` only on screens that need the selections, such as the preferences editor or discovery. No user ID route parameter is used—identity comes from the authenticated session. Routine profile requests do not load skill/category child collections.
- Persisted preferences and one-off search choices are different: skipping a wizard step for one search must not clear stored preferences. Applying category selections to opportunity search is YOM-1258/YOM-1262, not automatic in this API change. The Job Industry field is separate and must not be substituted for categories.

- Save and reopen each preference, then clear it; omitted fields clear on complete PATCH, so changing one wizard step must preserve all other selections.
- Select Accessibility Other and verify the description is required; deselect it and clear the text. Never send these preferences to a provider without the separate consent flow.
- Select a self-attested skill; verify it is labelled unverified. Already-verified skills are disabled in the picker. After promotion by a non-Job completion, refresh both resources and remove it from the self-attested draft.
- Save country plus a city centroid, reload profile, and reopen the location editor. Confirm longitude/latitude are not swapped and source round-trips through the UI mapping.
- Save only countryId on the location route: optional details clear, country remains selected. Missing/empty/unknown/Worldwide country must fail.
- Change country in the full profile editor: do not retain the prior country's city/region. Verify the identity-provider country follows the change, but no new location/preference attributes are written there.
- Save an unrelated profile field without losing loaded location data. Both profile save routes refresh the session profile. An incomplete provisioned profile must complete the existing required profile fields before the location shortcut can save.
- Confirm no automatic opportunity matching or distance filtering is implied by a successful preferences/location save.

## Gotchas

- The consolidated CF migration is still unreleased. If it gets applied in any environment before this `Type` addition lands, a new forward migration will be required; do not edit an already-applied migration in that case.
- The first preferences PATCH creates the parent `Entity.UserPreferences` row before writing category, accessibility or language links. A GET for a user without that row returns null scalar selections and empty preference-link lists; self-attested skills still load independently from `UserSkills`.
- The `UserSkills` unique `(UserId, SkillId)` constraint prevents dual rows for self-attested and verified versions of one skill.
- A stale UI selection containing a newly verified skill is rejected on PATCH; the UI should refresh preferences/skills and remove that ID from the self-attested selection.
- The IXO and Umuzi sample JSON resources retain source `Online`, not Yoma's `Remote`; each partner client maps its own incoming value before lookup resolution. CSV import and the ordinary lookup service remain canonical-only.
- UserPreferences returned by repository Query is a projection, not an EF-tracked domain object. The post-commit read in PATCH is intentional until link/skill writers maintain that projection in memory.
