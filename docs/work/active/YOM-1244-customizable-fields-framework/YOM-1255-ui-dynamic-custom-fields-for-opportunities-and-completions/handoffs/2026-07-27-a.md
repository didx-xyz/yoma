## What Was Done

**T2 — completion capture and display, and list cards.**

- **MyOpportunity definitions** — `getMyOpportunityCustomFieldDefinitions(opportunityId)` hitting
  `GET /myopportunity/{opportunityId}/custom/field/definition` (the opportunity type is resolved
  server-side), plus `useMyOpportunityCustomFieldDefinitionsQuery`.
- **Multipart completion submit** — `api/services/myOpportunities.ts` appends `CustomFields` as a
  single JSON-encoded form field alongside the existing verification files; the rest of the model
  is spread into the same `FormData`.
- **`OpportunityCompletionEdit` rewritten around the shared editor** (≈414 lines changed, mostly
  removed) — the fixed completion form became the definition-driven one, reusing `CustomFields`
  and its exported validators rather than duplicating rendering rules.
- **`OpportunityCompletionRead` + `MyOpportunityCustomFieldsSection`** for the read side, and
  custom-field metadata on `MyOpportunity/OpportunityListItem` so the four user lists
  (pending / saved / completed / declined) label completion values consistently.
- **`useSkillsQuery`** added and wired into `CustomFieldsView`, so Skill-lookup values resolve to
  names instead of showing GUIDs in read-only views (page size 500, lazy — only when a shown
  definition references Skill).
- Custom fields added to the opportunity **preview** component so the wizard preview matches the
  saved detail view.

## Gotchas

- ⚠️ **Completion submits `multipart/form-data`** — `CustomFields` is _one_ JSON string field, not
  repeated form entries. Sending it as repeated entries fails model binding.
- ⚠️ Completion definitions are keyed by **opportunity id**, not by type — the API resolves the
  type itself.
- The Skill lookup is a paged search, so the 500-row query is a pragmatic cap, not a guarantee that
  every referenced skill resolves.
