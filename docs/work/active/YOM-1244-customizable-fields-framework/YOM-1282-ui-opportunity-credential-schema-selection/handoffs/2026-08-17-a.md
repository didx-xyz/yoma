## What Was Done

Step 7 (Credential) of the Opportunity create/edit wizard now selects a type-aware schema.

- **Type-scoped discovery.** `useOpportunitySchemasQuery` takes a `typeContext` — the selected
  Opportunity type's stable `name` — passes it to `GET /ssi/schema`, and carries it in the query
  key so each type caches separately. It stays disabled until a type is resolved, because without
  a context the API returns schemas scoped to every other type as well.
- **Grouped selector.** Generic schemas under "All opportunity types", type-specific under the
  selected type's `displayName`. Labels are `schema.displayName`; the submitted value is
  `schema.name`, the full provider name, verbatim.
- **Clear on type change.** Changing the Opportunity type drops the current selection — generic
  included — leaving the step's own "Schema is required." to prompt reselection.
- **Attribute preview fixed.** The read-only table under the selector listed
  `entities[].properties` only, so a type-specific schema would have rendered without the custom
  fields it exists to carry. It now merges `properties` and `customFields` in the API's
  presentation order.
- **Two shared extractions.** `byPresentationOrder` / `groupLabelOf` moved out of
  `SchemaAttributesEdit.tsx` into `lib/credentials/attributePresentation.ts`; `SelectOptionGroup`
  moved into `api/models/lookups.ts`. Both had been local to the admin picker and now have a second
  consumer here (and a third coming in YOM-1283).
- **Opportunity Type dropdown shows `displayName`** rather than `name`, so it agrees with the
  schema group heading.
- **The schema lookup was then mocked** (second pass, same day) because the credential provider went
  offline and `SSISchemaService.ListInternal` reaches it for every schema resolution. The hook reads
  through YOM-1281's existing `credentialSchemaAdmin` façade, so one place still governs all schema
  traffic. The flag is gated on `NEXT_PUBLIC_ENVIRONMENT === "local"`, so the mock cannot reach a
  deployed build.
- **Mocked ⇄ live is switchable per session**, from the banner on the admin pages and the notice on
  the Credential step. The façade now resolves its implementation per call from `localStorage`
  instead of once at module load, so testing against the real API no longer needs a rebuild.
- **Fixed: the Credential step rendered nothing on load.** `watchStep7("credentialIssuanceEnabled")`
  was stale — the step has no issuance control of its own, and the effect deriving the value from
  verification wrote only to `formData`, which step 7's react-hook-form state is seeded from at
  mount and afterwards re-seeded only by `resetStep7` on a step submit. The effect now writes the
  form copy too. This predates YOM-1282; the new elements simply made it visible.

## Manual Test Steps

The API must be running on `feature/custom-fields-framework`. The **schema lookup is mocked in local
development** — `SCHEMA_ADMIN_MOCK_ENABLED` in `src/web/src/api/services/credentialSchemaAdmin.ts`
is gated on `NEXT_PUBLIC_ENVIRONMENT === "local"` — so the
credential provider need not be up for steps 1–8, and the fixtures supply the type-specific schemas
that steps 4–7 need. An amber notice on the Credential step marks the data as mocked and carries a
**mocked / live** switch; the same switch is on the admin schema banner. Live is per session, held
in `localStorage`, and switching reloads the page so no mocked response survives in the query cache.

Fixture coverage, verified by driving the mock module directly:

| Opportunity type | Schemas offered                                |
| ---------------- | ---------------------------------------------- |
| Job              | `Default` (generic) + `Placement` (Job)        |
| Learning         | `Default` (generic) + `Certificate` (Learning) |
| Event, Task      | `Default` (generic) only                       |

**Step 9 (save) cannot pass while the credential provider is offline**, and that is not a web
problem: `AssertSSISchemaApplicable` resolves the submitted schema server-side through the same
provider client. Expect the API's error in the toast.

1. **Create, no type yet.** New opportunity, enable verification, go to Credential. The Schema
   dropdown is empty — no type is selected, so nothing is offered.
2. **Generic list.** Back to General, pick a type, return to Credential. `Default` appears under
   an "All opportunity types" heading.
3. **Required.** Leave it blank and press Next — "Schema is required."
4. **Type-specific group.** Pick **Job**. `Placement` appears under a second heading reading "Job";
   pick **Learning** and it is `Certificate` instead — `Placement` never shows for Learning, and
   neither shows for Event or Task.
5. **Clear on change.** Select a schema, go back to General, change the type, return. The selector
   is empty and the step is invalid again. Repeat with a _generic_ schema selected — it clears too.
6. **Reselect the same type.** Change the type away and back. The selection stays cleared; the
   previously chosen schema is offered again but must be re-picked.
7. **Attributes preview.** With `Placement` selected, the table lists its mapped custom fields
   interleaved with the statics in the API's presentation order — `[Sample] Placement Status`,
   `Completion Date`, `User Display Name`, `[Sample] Application Deadline`, `[Sample] Salary`,
   `[Sample] Work Type`, `Type`, `Skills`, then the ungrouped system properties last.
8. **Edit, unchanged type.** Open an existing opportunity that issues `Opportunity|Default` — the
   fixture uses that exact full name, so a real opportunity's saved selection resolves against it.
   It shows on arrival and survives paging through the steps.
9. **Save.** Blocked while the provider is offline (see above); retry once it is back, then reopen
   and confirm the same schema is selected.
10. **Server-side rejection.** Optional, and also needs the provider: force a schema name scoped to
    another type into the request. The API's "not applicable to opportunity type" message surfaces
    in the error toast.

## Gotchas

- **The clearing effect is guarded on a previously known type, and must stay that way.** The
  Opportunity type lookup is a client query with no SSR prefetch, so `selectedTypeName` is `null`
  on first render and resolves a tick later. Comparing without the guard reads that `null → Job`
  transition as a type change and silently wipes the saved schema on every edit.
- `typeContext` resolves against the Opportunity type's **`name`**, never `displayName` — an admin
  renaming a type must not break existing schemas. `displayName` is for labels only.
- The API throws `ArgumentException` if `typeContext` is passed without a `schemaType`, or with one
  that does not resolve. The hook always sends `SchemaType.Opportunity`, so this only bites if
  someone reuses it for another schema type.
- `schemasOptions` is grouped, so react-select cannot resolve the current value from it —
  `schemasOptionsFlat` exists for that. Adding an option path that skips the flat list will show a
  blank selector with a value set behind it.
- While the schema list is loading, the selector renders its placeholder even on an opportunity
  that has a schema saved. It fills in on arrival; it is not a cleared selection.
- **`credentialSchemaAdmin.ts` is no longer admin-only** despite the name, and neither is
  `SCHEMA_ADMIN_MOCK_ENABLED`. Renaming both was rejected: it would invalidate YOM-1281's removal
  list for code that is deleted before the PR. The façade's doc comment names both consumers, so
  read that rather than trusting the filename.
- **The mock is web-only and cannot hide a provider outage.** Anything that resolves a schema
  server-side — opportunity save, credential issuance, the wallet — still calls the provider. If a
  schema-shaped failure appears while the flag is on, it is server-side by definition.
- **The mocked/live choice persists in `localStorage`** (`yoma.schemaMockMode`), so a session left
  on live stays on live across restarts. If mocked data unexpectedly does not appear, check the
  banner before suspecting the code.
- **`schemaMockActive()` is read per call, deliberately.** Queries call it directly rather than
  through the React hook, so they can never be a render behind the switch. The hook exists only so
  the banner's own appearance settles after mount without a hydration mismatch — the server cannot
  see `localStorage`. Do not "simplify" the queries onto the hook.
- The admin pages skip their SSR prefetch whenever `SCHEMA_ADMIN_MOCK_ENABLED` is set, which is what
  makes a client-side switch possible at all. Restoring the prefetch while the mock exists would
  server-render one data source and hydrate the other.
- Switching to live on an admin fixture URL (`/admin/schemas/Opportunity%7CJob%7CPlacement`) 404s,
  since that schema only exists in the fixtures. Expected — switch back or go to the list.
