## What Was Done

- Read the upgrading guide entries from 26.4.1 to 26.8.1 and checked each one against our realm, providers, theme and Helm values. The ones that affect us are in `feature.md`.
- Bumped the Keycloak image to 26.8.1 and keycloak-config-cli to `6.5.1-26.5.5`. Rebuilt the provider JARs against 26.8.1.
- Fixed the two realm import failures on 26.8.1 (`realm-management` 403, duplicate delegation scope on fresh import). Kept the password fields on the registration form.
- Ran the local compose stack under a separate project name (`docker compose -p kcupgrade`):
  - Ran a 26.4.0 baseline with the old files. The import passed and I created a test user with a password.
  - Swapped in the new images, JARs and export on the same database. Keycloak migrated the model (26.4.3, 26.6.x, ... 26.8.x) and logged no errors. keycloak-config-cli imported all three files.
  - Registered with email and password through the phone theme. The verification mail arrived in Mailpit and the link verified the email. The password was stored at registration.
  - The pre-upgrade user logged in through "Browser with phone".
  - Ran the full compose stack, API included, on 26.8.1. A registration through the login pages (driven with curl) sent `REGISTER`, and the login after email verification sent `LOGIN`. The API processed both and wrote the user to `Entity.User` with `EmailConfirmed = true` and `DateLastLogin` set.
  - `keycloak-users` (`users.sh`, also the Helm post-install hook) created the four test users and their role mappings on 26.8.1.
  - Ran a fresh install on an empty database with the final files. The import passed and Keycloak logged no errors.
- Ran the same scripted checks against the full stack (Keycloak, API, Mailpit) on `master` (26.4.0) and on this branch (26.8.1), each from empty volumes, and diffed the output. About 70 checks:
  - Email registration, verification mail and link, password login, token contents (claims, audience, scopes, roles), userinfo, introspection by `yoma-api`, refresh, logout.
  - `kc_action=UPDATE_PROFILE` and its webhook, password reset by email, phone registration and phone OTP login (test number), `maza-app` client credentials creating a user through `POST /api/v3/externalpartner/user`.
  - Admin token and `POST /api/v3/user/search`, `sa-yoma-api` admin calls, `p2e-green` code flow with a client secret, a rejected look-alike redirect host, brute-force lockout, the login, account and admin console pages and every login theme resource.
  - Only three things differed, all expected:
    - `refresh_expires_in` went from `0` to `2592000` (offline tokens now carry an expiry, 26.8.0). `src/web` does not read this field.
    - A phone-only registrant no longer gets a `VERIFY_EMAIL` required action. 26.4.0 added it and then skipped it because there is no email, so the user saw no difference. 26.8.1 does not add it.
    - The API processed three more `LOGIN` webhooks on 26.8.1, because of the change above. On 26.4.0 the scripted phone logins stopped at the skipped `VERIFY_EMAIL` step, which the script did not follow.
- In a real browser (T3 preview) on 26.8.1: phone registration with a non-test number. The dummy SMS provider logged the code, the theme's Vue and intl-tel-input scripts ran, and the user was created with `phoneNumberVerified = true`. The API processed `REGISTER` and `LOGIN`. The admin console loaded and listed the `yoma` clients.
- Called the admin endpoints the API uses directly with `sa-yoma-api` on 26.8.1: update user, send verify email, execute actions email (mail arrived in Mailpit), and add a realm role. All returned 204.
- Upgraded an existing 26.4.0 Helm deployment on a local kind cluster the way CI does it, with two replicas and with one. Results are in `feature.md` under "Helm upgrade test". The two-replica path logged out sessions created during the overlap, and a rollback after migration took the login page down.
- Bumped the Datadog init library versions for Keycloak, the API and the web app, and checked each tracer locally on arm64. Details are in `feature.md` Decisions.

## Gotchas

- See `feature.md` Gotchas. The Prod rollout one matters most.
- `PATCH /api/v3/user` returned 500 on both versions locally, because it calls Aries CloudAPI (SSI), which is not configured in compose. The API's own `UpdateUser` call to Keycloak was therefore not exercised through the API; the same admin endpoint was called directly instead.
- Found on both versions, so not caused by this upgrade: after `UPDATE_PROFILE`, Keycloak held the new names but `Entity.User` kept the old (empty) ones, although the API logged the event as processed. The webhook handler reads the user back from Keycloak straight away and probably sees it before Keycloak commits [INFERENCE].
- Also outside this upgrade, from reading the code (not run): `KeycloakClient.RemoveRoles` calls `PostUsersRoleMappingsRealmByUserIdAsync`, which adds roles. Removing `OrganisationAdmin` would add it back instead.
